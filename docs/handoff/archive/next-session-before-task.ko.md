# 다음 세션 시작 프롬프트

아래 블록을 새 세션의 첫 메시지로 붙여 넣는다.

```text
~/TURTLE에서 TLS 1.3 벤치마크 프레임워크 개발을 이어가자. 먼저 docs/handoff/README.ko.md, docs/build-contract.ko.md, include/turtle/implementation.hpp를 읽고 실제 git status와 코드를 대조해라. /tmp의 실험본이나 과거 대화로 현재 상태를 추정하지 마라.

~/TURTLE은 개인 저장소다. 별도 브랜치 없이 main에서 직접 작업하고, 필요하면 로컬 Git 이력을 자유롭게 정리해라. 현재 설계에서 더는 쓰지 않는 레거시는 하위 호환을 위해 남겨두지 말고 휴지통으로 옮겨라. 단, 진행 중인 작업이나 사용자의 활성 제출물을 미커밋 상태라는 이유만으로 레거시로 보지는 마라.

불변 원칙은 SUPERCOP식 편의성과 계측의 엄밀성이다. 개발자가 이미 가진 빌드 정보를 다시 적게 하지 말고 연구자의 선택을 추측하지 마라. TLS 원본과 TURTLE은 서로 몰라야 한다. 구현체 API와 공통 선언을 함께 아는 코드는 개발자의 implementation.cpp 하나다. implementations/는 사용자 전용 슬롯이고 벤더별 레시피는 docs/의 선택형 예시일 뿐이다. 자동 선택·폴백·벤더 등록·플러그인·Python 의존성을 추가하지 마라.

bench.sh가 사용자의 build.sh와 두 역할의 최종 링크를 책임진다. 같은 제출로 두 역할을 만들되 한 연결에서는 한쪽만 계측한다. 목표는 구현체 순위나 보안 감사가 아니라 주어진 조건에서 개별 구현체가 보인 성능이다. S0–S4의 의존성을 지키고, S2/S4에서 CF와 SAD₁의 관측 순서를 강제하지 마라. 측정할 수 없는 사건을 만들어내지 마라.

지난 단계에서 확인한 것은 빌드 편의성이다. 빌드·링크 성공을 PQTLS 지원이나 성능 지표 검증으로 해석하지 마라. sh tests/submission-build-contract.sh로 빌드 경계를 먼저 확인해라. 내가 다른 우선순위를 주지 않았다면, 다음은 현재 코드에서 doctor·예열·본 시도와 각 연결의 setup·실행·정리·실패 처리가 어떻게 이어지는지 S0 기준으로 대조해라. 이미 구현된 것, 빈틈, 사용자 결정이 필요한 것을 구분하고, 다음에 손볼 가장 작은 단위와 회귀 테스트를 제시해라. 바뀌는 명세나 문서도 함께 짚어라.
```
