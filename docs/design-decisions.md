## 실행 수명주기 — 먼저 구현할 것

**확정: 연결 한 건의 시작·진행·종료는 TURTLE이 지시한다.** TURTLE은 새 시도를 시작하고, 성공·실패를 기록하고, 해당 시도의 정리를 지시한다. 구현체 고유의 TLS 자원은 구현체가 생성·해제한다. 준비 중간에 실패해도 이미 확보한 자원은 정리한다. 개발자가 시나리오 반복문이나 실패 복구용 실행기를 별도로 작성하는 구조가 아니다. 실제 TCP `connect`/`accept`의 호출 주체와 준비·해제 함수의 시그니처는 아직 정하지 않았다.

### doctor

**확정: `doctor`는 예열 전에 실제 시나리오를 처음부터 끝까지 한 번 수행하고 계측하는 진단이다.** 설정이 맞는지, 구현체를 불러올 수 있는지, 훅 하나가 작동하는지만 검사하고 끝내지 않는다. TURTLE이 기존 함수 계약으로 시나리오를 구동한다. 개발자에게 별도의 진단용 함수를 구현시키지 않는다.

진단 결과는 다음 두 질문에 따로 답해야 한다.

1. **시나리오가 완주했는가?** 실패했다면 어느 단계에서 실패했는가?
2. **이 구성에서 어떤 지표를 실제로 얻었는가?** 한 지표의 통과 여부만 보여주는 대신, 얻은 지표와 얻지 못한 지표를 함께 알린다. 이유를 확인할 수 없으면 불명으로 남긴다. 예를 들어 교환과 벽시계 계측은 성공했지만 CPU 카운터 접근은 불가능할 수 있다.

| 단계 | 목적 | 결과의 용도 |
|---|---|---|
| `doctor` | 실제 교환과 계측 경로가 동작하는지 확인 | 진단 1회의 관측 결과. 예열 횟수나 본 측정 표본 수에 합산하지 않는다. |
| 예열(warm-up) | 본 측정 전 같은 작업을 미리 수행 | 예열 기록. 예열을 0회로 설정하는 것과 진단을 생략하는 것은 다르다. |
| 본 측정 | 요청한 조건에서 성능 표본을 얻음 | 각 시도의 실제 결과. 진단 1회 성공이 이후 시도의 성공을 보장하지 않는다. |

**미결: 진단의 범위.** 면담에서 말한 “전체 시나리오”가 개별 시나리오의 전체 흐름을 실제로 계측한다는 점은 확정이다. 한 번의 `doctor`가 요청한 시나리오 하나를 대상으로 하는지, 같은 구현체에서 S0–S4를 모두 점검하는지는 구분해서 결정한다. 단독 명령과 일반 실행의 관계, 필수 지표가 없거나 확인되지 않을 때 본 측정을 중단하는 규칙도 아직 확정하지 않았다.

## 앞선 면담에서 정한 원칙

- **무엇을 벤치마크하는가.** SUPERCOP에서 가져올 원칙은 사용 편의성과 측정의 엄밀성이다. 목적은 TLS 구현체 간 순위나 보안성 평가가 아니라, *이 구현체가 이 설정·상대·계측 조건에서 보인 성능*을 재는 것이다. RFC 9846의 TLS 1.3 전체 핸드셰이크를 따른다고 전제한다. 서버 인증·mTLS는 구현체의 정상적인 인증 절차를 사용한다. TURTLE이 인증서 검증의 정확성을 재감사하지 않는다는 뜻이지, 인증을 끈다는 뜻이 아니다.
- **개발자가 제공하는 접점.** 구현체를 불문하고 TURTLE이 선언한 C 함수의 시그니처와 동작 조건에 직접 연결한다. **별도 어댑터나 벤더 등록은 없다.** 특정 TLS 구현체에 종속되지 않는 순수 C/C++ 프레임워크가 목표다. 기존 구현체와 빌드 정보를 바탕으로 빌드·링크를 자동화한다. 인증 방식, 인증서·키 경로, 상대 이름, 로컬 또는 원격 주소·포트는 설정값이지 각각 개발할 함수가 아니다. 빌드 정보의 형식과 원격 프로세스 배포·기동 방식은 미결이다.
- **한쪽만 계측한다.** 한 연결에서 클라이언트 또는 서버 중 한쪽만 대상이다. 상대는 정상적인 시나리오 동작을 하는 비계측 블랙박스다. 대상의 TLS↔TCP 경로에는 하위 송신 시도 직전·데이터 수신 직후에 TURTLE의 훅을 호출할 자리가 필요하다. OpenSSL BIO 자체를 요구하지 않는다. CAD·SAD를 무엇으로, 얼마나, 언제 보낼지는 TURTLE이 지시하고 구현체는 자기 TLS의 읽기·쓰기를 수행한다.
- **대상 쪽의 계측 깊이.** 블랙박스 실행은 핸드셰이크 메시지별 계측 없이 시나리오의 두 경계를 본다. 화이트박스 실행은 상세 관측과 사후 분석을 더한다. 이는 상대까지 계측하겠다는 뜻이 아니다. 암호화된 묶음에서 레코드 범위를 역산할 수 있는 경우와, 내부 메시지 각각의 시각까지 관측한 경우를 구별한다.
- **공식 지표.** 벽시계 지연은 그 자체로 정식 결과다. 하드웨어 카운터를 쓸 수 없다는 이유만으로 유효한 지연을 버리지 않는다. `cycles`는 해당 구간을 실행한 **계측 대상 스레드의 사용자 공간 하드웨어 사이클**이다. 상대편·작업 스레드·커널까지 포함한 구현체 전체 비용이나 경과 시간에서 환산한 추정치가 아니다.

## 최종 명세 면담: 빌드 입력

- **확정 1 — 사전 빌드는 제출 요건이 아니다.** 개발자는 TLS 프로젝트의 원래 구조와 빌드 파일, 공통 함수 계약을 구현한 `implementation.cpp`가 담긴 폴더 하나를 낸다. 생성 헤더나 라이브러리가 없어도 TURTLE이 원본 빌드 절차를 실행하고 그 산출물로 요청한 클라이언트·서버를 링크하는 것이 목표다. 빌드 방법을 결정할 수 없으면 부족한 정보를 알리고 멈추며 시스템 TLS로 대체하지 않는다.
- **확정 2 — 빌드 옵션은 선택 입력이다.** 추가 옵션을 지정하지 않으면 제출된 원본 빌드 절차를 그 설정 그대로 실행한다. 스크립트 안의 최적화 옵션도 이 설정의 일부다. 연구자가 다른 구성을 원하면 원본 소스를 수정하지 않고 옵션을 별도로 지정할 수 있어야 한다. 제출물에 남지 않은 과거 빌드 옵션을 추측하지 않는다.
- **확정 3 — TURTLE은 외부 TLS 구현체를 몰라야 한다.** 공통 계약을 만족하는 새 구현체나 포크로 제출 폴더를 바꿔도 TURTLE의 빌더, 클라이언트·서버, 시나리오 코드나 지원 목록을 고치지 않는다. OpenSSL은 이 경계를 시험하는 예시일 뿐 기준 구현이나 기본 링크 대상이 아니다. 제출한 `implementation.cpp`가 벤더 헤더를 포함하거나 원본 빌드 명령·산출물 경로에 벤더 이름이 등장하는 것은 문제없다. 그 이름이나 소스 트리의 특징으로 TURTLE이 전용 API·명령·라이브러리를 선택하는 것이 금지된다.
- **확정 4 — `implementation.cpp`는 유일한 코드 접점이며 TURTLE이 컴파일한다.** 개발자는 이 파일에서 TURTLE 공통 헤더가 선언한 함수 7개를 자기 TLS API에 연결한다. TURTLE은 선택한 TLS 빌드의 헤더·컴파일 설정을 사용해 이 파일을 컴파일하고, 그 결과를 같은 빌드의 링크 입력과 함께 요청한 역할의 실행 파일에 연결한다. 원본 TLS 프로젝트의 빌드에 `implementation.cpp`를 등록할 필요는 없다. 원본 빌드 명령과 컴파일·링크 입력을 전달하는 것은 빌드 정보의 전달이지 두 번째 코드 접점이 아니다.
- **미결.** 구현체에 무관하게 원본 빌드를 호출하는 접점, 옵션을 전달하는 형식과 단계, `implementation.cpp` 및 두 실행 파일을 빌드할 때 쓸 생성 헤더·링크 대상의 전달 방식은 아직 정하지 않았다. TURTLE 전용 빌드 레시피를 필수 제출물로 정한 것이 아니다.

기존 빌드 스크립트가 제출된 경우, 위 결정에서 말하는 ‘원본 빌드’는 **사용자의 별도 사전 작업이 아니라 TURTLE이 요청한 역할 실행 파일을 만드는 과정의 선행 작업**이다. 스크립트는 구현체 고유의 설정·코드 생성·컴파일을 그대로 수행한다. TURTLE은 그 빌드의 헤더와 컴파일 설정으로 `implementation.cpp`를 컴파일하고, 그 빌드의 링크 입력으로 역할 실행 파일을 완성한다. TURTLE 공통 소스까지 원본 스크립트에 넘기는 뜻은 아니다. 스크립트의 호출 방법을 아는 것과 그 결과의 사용 방법을 아는 것은 구분한다.

### 비교 근거: SUPERCOP의 `crypto_aead` 제출물

[공식 제출 안내](https://bench.cr.yp.to/call-aead.html)의 최소 예는 `api.h`와 두 AEAD 함수를 정의하는 C 소스다. 실제 `tinyjambu128v2/ref`에도 이 두 파일만 있다. SUPERCOP의 일반 C/C++ 경로는 [프리미티브 아래에서 `api.h`를 찾아 그 디렉터리를 선택](https://github.com/jedisct1/supercop/blob/200cd30ca1f501463bd5cdd3da115a20d688d8fb/do-part#L440-L445)하고, [작업 디렉터리로 복사한 뒤 바로 아래 소스를 열거](https://github.com/jedisct1/supercop/blob/200cd30ca1f501463bd5cdd3da115a20d688d8fb/do-part#L519-L537)한다. SUPERCOP이 `crypto_aead.h`를 생성하고 소스를 직접 컴파일해 자기 검증·계측 프로그램과 링크한다. 제출 폴더의 `Makefile`을 실행하는 규약이 아니며, 독립 빌드 가능 여부가 판정 기준도 아니다.

같은 리비전의 `do-part`로 TinyJAMBU-128v2 참조 구현을 새 이름으로 복사해 검증했다(격리된 amd64/GCC 한 구성). 구현 폴더에 `Makefile`이 없는 경우와, Make가 읽으면 표식을 남기고 기본 타깃은 실패하게 한 파일을 넣은 경우 모두 개별 대상 명령이 종료 코드 0으로 끝났다. 두 실행 모두 원본 small/big 체크섬과 일치했고 암호화·복호화 계측 결과가 나왔다. 표식은 같은 파일을 GNU Make로 직접 읽힌 대조군에서만 생겼다. 축소 사본의 공통 `init`은 마지막 진단 파일 조회에서 종료 코드 1을 반환했으며 시험에 필요한 산출물은 확인했다. 이는 해당 C 구현의 빌드 경로를 검증한 것이지 전체 SUPERCOP 빌드 검증은 아니다.

이 선례가 설명하는 것은 **약속한 함수로 프레임워크의 프로그램을 빌드하는 단계**다. **임의 TLS 원본의 설정·코드 생성·라이브러리 빌드까지 추론하는 방법**의 선례로 쓰지 않는다. TURTLE에서 이 두 단계를 어떻게 연결할지는 아직 미결이다.

### 비교 실험: 원본을 빌드하는 절차와 그 결과를 사용하는 정보

이것은 빌드 계약을 고르기 위한 실험이지 제품 기능이나 합의된 제출 형식이 아니다. 네이티브 C 라이브러리 두 개를 대상으로 같은 역할 소스와 공통 C 선언을 썼다. 각 제출물의 `implementation.cpp`는 프레임워크 쪽에서 구성당 한 번만 컴파일했다.

- **CMake 제출물:** 원본 디렉터리와 사용할 라이브러리 타깃 이름을 지정했다. 원본을 하위 프로젝트로 포함하자 그 타깃이 공개한 생성 헤더 경로와 컴파일 정의가 `implementation.cpp`에 전달됐다. 역할 소스에는 두 설정이 전파되지 않았고 클라이언트·서버가 모두 통과했다. 이는 같은 빌드 안에 참여할 수 있고 필요한 사용 정보를 선언한 타깃의 경우다. 별도로 구성한 프로젝트의 타깃 이름만으로는 같은 효과를 얻지 못한다. [CMake 타깃의 사용 정보](https://cmake.org/cmake/help/latest/manual/cmake-buildsystem.7.html#target-usage-requirements) · [다른 빌드에서 타깃 가져오기](https://cmake.org/cmake/help/latest/guide/importing-exporting/index.html)
- **셸 제출물:** 기존 스크립트를 실행하고 생성 헤더 경로와 정적 라이브러리 두 개를 링크 순서대로 지정했을 때 두 역할이 모두 통과했다. 같은 스크립트가 두 파일을 정상적으로 생성해도, 두 번째 라이브러리를 링크 입력에서만 빼자 두 역할 모두 미해결 심볼로 링크에 실패했다. 스크립트의 종료 코드와 파일의 존재만으로는 사용 방법을 알 수 없다.

검증 범위는 축소한 C/C++ 빌드·링크·실행이다. 실제 TLS, 교차 컴파일, 증분 빌드 또는 임의 프로젝트 자동 인식을 검증한 것은 아니다. 두 트리를 같은 작업공간에 놓는 것과 원본 빌드 규칙을 버리고 소스를 한꺼번에 컴파일하는 것은 별개의 선택이다.

## 라이프사이클 이후에 이어갈 계측 논의

- **수신·송신의 끝.** S1 서버가 재려는 것은 CAD의 수신까지이지 이후 내용 검사나 처리 완료까지가 아니다. S3·S4에서 요청 수신과 응답 송신 사이를 관측해도 그 차이 전체를 순수 요청 처리 시간이라 할 수 없다. S4에서 요청의 답은 선행 인사 SAD₁이 아니라 SAD₂다.
- **응답 크기와 첫 바이트.** 처음에는 첫 응답 평문 반환(②)을 선호했고, 이어서 *보낼 SAD의 분량을 먼저 정하고 대상 분량의 마지막 수신 직후 또는 마지막 송신 직전을 보자*는 방향을 제시했다. 첫 응답과 전체 응답은 다른 질문이다. BIO·소켓의 암호문 수신을 앱의 첫 평문 반환과 동일시하지 않는다. S0–S4별 정확한 관측 층·시작점·기본 끝점, TTFB와 전체 수신 시간의 공개 방식은 보류한다.
- **TCP 순번의 동기.** S2·S4에서는 SF 이후 선송신 인사와 CF가 반대 방향으로 겹칠 수 있다. SEQ로 관심 레코드의 바이트를 실은 세그먼트를 찾고 **바로 그 사본의 누적 ACK**로 반대 방향 레코드 끝까지 TCP가 받았는지를 판단한다. ACK가 부족하면 선후 미확정이며, 충분해도 TLS 복호화나 앱 읽기를 증명하지 않는다. 이는 선택적 전송 분석이지 기본 타이머나 개발자가 구현할 함수가 아니다. [현재 분석의 두 방향 판정](../src/native/packets.cpp#L118-L127)

이 논의에서 확인한 근거는 설계 결정과 구별한다.

- Paquin 등의 *Benchmarking Post-Quantum Cryptography in TLS* §4.2는 핸드셰이크 완료를, §4.3·그림 3은 크기가 다른 HTML 파일을 끝까지 받는 시간을 다룬다. 후자가 첫 바이트를 재는 실험이라는 뜻은 아니다.
- Sosnowski 등의 *The Performance of Post-Quantum TLS 1.3* §4는 외부 패킷 시각을 이용하는 실행과 `perf`를 이용하는 별도 실행을 구분한다. TURTLE이 차용한 원칙은 계측 영향의 분리이며, 관측 위치가 같다는 뜻은 아니다.
- 옛 `docs/for-paper/PQTLS 벤치마크 프레임워크 제안_ver1.md` §7.1과 보관된 S2 실험 12건을 확인했다. 동일한 서버 소켓 호출 순서에서도 인사 전체 수신이 CF 사본 송신에 선행한 경우, 반대 방향의 선후가 확인된 경우, 어느 쪽도 확인할 수 없는 경우가 각각 4건이었다. 이 기록은 S4의 근거를 대신하는 실측값이 아니다.

## 현재 구현과 문서에 미치는 영향

- [현재 `check`](../src/native/stream.cpp#L950-L962)는 실행 설정을 검증하고 `capability: null`을 출력한다. [현재 예열 루프](../src/native/stream.cpp#L1031-L1044)에는 본 측정 진입 판정이 있다. 어느 쪽도 위에서 합의한 `doctor`를 구현한 것은 아니다.
- [README의 빌드·실행·결과 안내](../README.md)에는 직접 연동한 구현체의 준비, 진단·예열·본 측정의 구분, 지표별 가용성을 반영해야 한다. 현재 README의 PMU 기반 표본 자격과 목표 설계의 정식 벽시계 결과는 구별한다.
