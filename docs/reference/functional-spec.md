# TURTLE 기능 요구사항 명세

이 문서는 TURTLE 프레임워크가 **무엇을, 어디서, 어떻게, 어느 단위까지** 재야 하는지를 정합니다. 작업 지시서(`/tmp/turtle-work-order.md`)의 모든 작업은 이 명세를 기준으로 합니다. 배경과 이유는 인계 문서(`~/TURTLE/README.md`)에 있습니다.

작성일은 2026년 10월 14일입니다.

---

## 0. 이 명세를 읽는 법

### 0.1 요구 수준

| 표기 | 뜻 |
|---|---|
| **필수** | 반드시 지켜야 합니다. 지키지 못하면 그 기능은 끝나지 않은 것입니다. |
| **권장** | 특별한 이유가 없으면 지킵니다. 지키지 않았다면 이유를 `docs/DECISIONS.md`에 적습니다. |
| **선택** | 해도 되고 하지 않아도 됩니다. |

### 0.2 요구사항 번호

요구사항마다 `FR-영역-번호` 형태의 번호를 붙였습니다. 테스트와 커밋 기록에서 이 번호를 인용하면, 어느 요구사항을 확인했는지 추적할 수 있습니다.

| 영역 | 뜻 |
|---|---|
| DEF | 용어 |
| SCOPE | 범위 |
| CON | 구현자와의 계약 |
| RUN | 실행 절차 |
| EVT | 사건 |
| SEG | 토막 |
| LVL | 관측 수준 |
| MET | 계측값 |
| DER | 원자료에서 계산하는 값 |
| CFG | 설정 프로필 |
| VAL | 무효 판정 |
| ENV | 측정 환경 |
| CAP | 계측 도구 점검 |
| REC | 원자료 |
| INT | 키 로그 해석기 |
| STAT | 통계와 보고 |
| CAL | 계측 비용 보정 |
| TEST | 받아들임 시험 |
| MOD | 코드 구조와 모듈화 |

### 0.3 이 명세가 바뀌는 조건

이 명세는 인계 문서 4절의 원칙을 구체화한 것입니다. 원칙과 부딪히는 변경은 연구자의 확인 없이 하지 않습니다. 원칙 안에서의 세부 변경은 이유를 적고 할 수 있습니다.

---

## 1. 용어 (FR-DEF)

- **FR-DEF-1 엔드포인트와 역할:** 엔드포인트는 TLS를 실행하는 클라이언트나 서버입니다. 역할은 `Client`와 `Server` 둘뿐입니다.
- **FR-DEF-2 측정 한 번(표본):** 지휘 프로세스가 새로 띄운 서버 프로세스와 클라이언트 프로세스 한 쌍이, 셋업부터 정리까지 라이프사이클을 한 번 도는 것입니다. 한 번의 측정은 연결을 하나 이상 포함할 수 있습니다.
- **FR-DEF-3 시나리오:** 한 번의 측정 안에서 연결을 몇 개, 어떤 순서로, 어떤 출발 상태에서 돌릴지 정한 것입니다. 예를 들어 "측정용 연결 1개(기본)", "데우기용 연결 1개와 측정용 연결 1개"가 있습니다.
- **FR-DEF-4 사건:** 시각을 찍을 수 있는 한 순간입니다. 사건마다 종류, 역할, 연결 번호, 관측 위치가 붙습니다(5절).
- **FR-DEF-5 토막:** 같은 역할, 같은 연결에서 이웃한 두 사건 사이의 구간입니다(6절). 토막은 프레임워크가 보장하는 측정의 가장 작은 단위입니다.
- **FR-DEF-6 관측 위치:** 사건의 시각을 어디서 찍었는가입니다. 위치는 구현체 경계, 시스템 호출 경계, 커널, 네트워크 카드(NIC), 선로 가운데 하나입니다.
- **FR-DEF-7 관측 수준:** 한 번의 측정에서 실제로 얻은 관측 위치의 묶음입니다(7절).
- **FR-DEF-8 라이브러리 호출:** 프레임워크가 구현자의 계약 함수를 한 번 부르는 것입니다.
- **FR-DEF-9 송수신 함수:** 프레임워크가 구현자에게 주는 함수로, 구현체는 모든 TLS 바이트를 이 함수로만 보내고 받습니다.
- **FR-DEF-10 흐름:** 한 엔드포인트가 상대의 응답을 기다리지 않고 잇달아 보내는 메시지 묶음입니다. 예를 들어 서버의 ServerHello부터 Finished까지가 흐름 하나입니다.
- **FR-DEF-11 원자료:** 측정 중에 기록한 사건과 계측값 전체입니다. 요약은 언제나 원자료에서 다시 만듭니다.
- **FR-DEF-12 무효 실행:** 정상 경로를 벗어나 결과를 쓰지 않는 측정입니다. 원자료에는 남기고 요약에서는 뺍니다(11절).

---

## 2. 범위 (FR-SCOPE)

- **FR-SCOPE-1 (필수):** 프레임워크는 암호군을 `TLS_AES_128_GCM_SHA256`으로 고정한 인증서 기반 TLS 1.3 전체 핸드셰이크만 잽니다. 서버만 인증하는 경우와 상호 인증을 다룹니다. 다른 암호군의 비교·협상은 범위 밖입니다.
- **FR-SCOPE-2 (필수):** 다음은 범위 밖이며, 생기면 그 측정을 무효로 합니다. HelloRetryRequest, PSK 사용, 세션 재개, 조기 데이터, 핸드셰이크 뒤의 클라이언트 인증, KeyUpdate, TLS 1.3이 아닌 버전의 협상입니다.
- **FR-SCOPE-3 (필수):** 패킷 손실, 재전송, 잘못된 메시지, 오류 경고, 빈 클라이언트 인증서를 다루는 기능은 만들지 않습니다.
- **FR-SCOPE-4 (필수):** 키 공유 값의 신선도 확인, 변조 거절 시험, 타이밍 누출 시험, 잘못된 인증서 거절 시험은 만들지 않습니다.
- **FR-SCOPE-5 (필수):** 측정의 끝은 클라이언트가 보낸 응용 데이터(핑)에 대한 서버의 응용 데이터(퐁)가 클라이언트에서 복호화된 때입니다. 핑과 퐁은 모두 응용 트래픽 키로 보호되어야 합니다.

## 3. 구현자와의 계약 (FR-CON)

계약은 `include/turtle/` 아래의 헤더로 정합니다. 프레임워크가 선언하고, 구현자가 정의합니다.

### 3.1 구현자가 정의할 함수

- **FR-CON-1 (필수):** 계약은 다음 함수를 포함해야 합니다. 이름은 바꿔도 되지만 뜻은 같아야 합니다.

| 함수 | 뜻 |
|---|---|
| `name()` | 구현체의 이름과 판을 돌려줍니다. 예: `openssl-3.x.y`. |
| `declare()` | 구현체의 선언을 돌려줍니다(FR-CON-6). |
| `setup(role, saved)` | 프로세스마다 한 번 불립니다. 라이브러리 초기화, 인증서와 키, 설정을 준비합니다. `saved`는 앞 측정이 남긴 컨텍스트이며, 없으면 `nullptr`입니다. |
| `open(role, io)` | 연결마다, 첫 TLS 바이트 전에 불립니다. `io`는 이 연결의 송수신 함수 묶음입니다. |
| `handshake_step(conn)` | 지금 할 수 있는 만큼 진행하고, `WantRead`, `WantWrite`, `Done`, `Failed` 가운데 하나를 돌려줍니다. |
| `peer_verification(conn)` | 라이브러리가 실제로 계산한 상대 인증서 검증 결과를 `Passed`, `Failed`, `NotApplicable` 가운데 하나로 돌려줍니다. |
| `negotiated(conn)` | 협상된 버전, 암호 방식, 키 교환 그룹, 서명 방식, 재개 여부를 돌려줍니다. |
| `app_send(conn, data)` | 응용 데이터를 보냅니다. 돌려주는 값은 `handshake_step`과 같습니다. |
| `app_recv(conn, buffer)` | 응용 데이터를 받습니다. 받은 평문의 길이와, `handshake_step`과 같은 값을 함께 돌려줍니다. |
| `close(conn)` | 연결 객체를 정리합니다. 소켓은 닫지 않습니다. |
| `save(role)` | 다음 측정에 넘길 컨텍스트를 바이트로 돌려줍니다. 비어 있으면 넘길 것이 없다는 뜻입니다. |
| `teardown(role)` | 프로세스마다 마지막에 불립니다. |

- **FR-CON-2 (필수):** 지금의 `exchange_app_data()`는 `app_send()`와 `app_recv()`로 나눕니다. 그래야 응용 데이터 단계에서도 프레임워크가 기다림을 맡고, 핑과 퐁의 송수신 사건이 따로 기록됩니다.

### 3.2 프레임워크가 구현자에게 주는 함수

- **FR-CON-3 (필수):** 프레임워크는 구현자에게 연결마다 송수신 함수 묶음을 줍니다. 구현자는 라이브러리의 입출력 콜백(OpenSSL의 BIO, wolfSSL의 송수신 콜백, Mbed TLS의 `set_bio`)에서 이 함수를 불러야 합니다.
  - `send(io, bytes, len)`는 실제로 보낸 바이트 수를 돌려주거나, 지금은 보낼 수 없다는 표시를 돌려줍니다.
  - `recv(io, buffer, len)`는 실제로 받은 바이트 수를 돌려주거나, 지금은 받을 것이 없다는 표시를 돌려주거나, 상대가 연결을 닫았다는 표시를 돌려줍니다.
  - 두 함수는 막히지 않습니다. 기다림은 프레임워크가 라이브러리 호출 밖에서 합니다.
- **FR-CON-4 (필수):** 프레임워크는 구현자에게 키 로그 함수를 줍니다. 구현자는 라이브러리의 키 로그 기능에서 이 함수를 불러, 비밀값의 이름표, 클라이언트 난수, 비밀값을 넘겨야 합니다. 이름표는 `CLIENT_HANDSHAKE_TRAFFIC_SECRET`, `SERVER_HANDSHAKE_TRAFFIC_SECRET`, `CLIENT_TRAFFIC_SECRET_0`, `SERVER_TRAFFIC_SECRET_0`, `EXPORTER_SECRET` 같은 것입니다.
- **FR-CON-5 (필수):** 프레임워크는 구현자에게 할당 함수 묶음(할당, 재할당, 해제)을 줍니다. 라이브러리가 할당 함수를 바꿔 끼우는 기능을 제공한다면, 구현자는 `setup()` 안에서 이것을 연결해야 합니다.

### 3.3 구현자의 선언

- **FR-CON-6 (필수):** `declare()`는 다음을 담아야 합니다.
  - 송수신 함수를 쓰는가, 아니면 소켓을 직접 쓰는가(호환 방식)
  - 할당 함수를 바꿔 끼웠는가
  - 키 로그를 넘기는가
  - 라이브러리가 별도 스레드를 만드는가
  - 컨텍스트에 무엇을 담는가(사람이 읽는 설명)
  - 적용한 경량화 기법(없으면 "없음")
  - 라이브러리의 빌드 옵션

### 3.4 구현자가 지켜야 할 규칙

- **FR-CON-7 (필수):** 구현체는 TLS 바이트를 송수신 함수로만 주고받아야 합니다. 호환 방식이라고 선언한 경우만 예외입니다.
- **FR-CON-8 (필수):** 구현체는 계약 함수가 불리지 않은 동안 일을 하면 안 됩니다. 별도 스레드가 불가피하면 선언해야 하며, 그 측정에는 "별도 스레드 있음"이 붙습니다.
- **FR-CON-9 (필수):** 컨텍스트에는 기법이 정상적으로 연결 사이에 들고 다니는 상태만 담습니다. 프레임워크는 이것을 검사하지 않고, 선언과 크기만 기록합니다(정직한 구현자 가정).
- **FR-CON-10 (필수):** `peer_verification()`의 결과는 라이브러리가 계산한 값에서 가져와야 합니다. OpenSSL이라면 `SSL_get_verify_result()`입니다. 검증 실패 시 핸드셰이크를 멈추는 설정을 써야 합니다.
- **FR-CON-11 (필수):** 구현자는 소켓을 닫으면 안 됩니다. 소켓은 프레임워크가 만들고, 확인하고, 닫습니다.

## 4. 실행 절차 (FR-RUN)

### 4.1 측정 한 번의 라이프사이클

- **FR-RUN-1 (필수):** 측정 한 번마다 서버 프로세스와 클라이언트 프로세스를 새로 띄웁니다. 한 프로세스에서 측정 여러 번을 돌리지 않습니다.
- **FR-RUN-2 (필수):** 각 역할 프로세스는 다음 순서를 정확히 따릅니다.
  1. 계측기 준비: 카운터를 열고, 기록 버퍼를 미리 잡습니다.
  2. 셋업: `setup(role, saved)`를 부릅니다.
  3. TCP 준비: 시나리오가 요구하는 수만큼 TCP 연결을 맺고 확인합니다(FR-RUN-5).
  4. 준비 신호: 두 역할이 모두 준비되었음을 지휘용 통로로 맞춥니다.
  5. 격리: 새 파일과 새 프로세스를 만들지 못하게 합니다(FR-RUN-7).
  6. 연결마다 차례로 `open`, `handshake_step` 반복, `peer_verification`, `negotiated`, `app_send`와 `app_recv` 반복, `close`를 진행합니다.
  7. 컨텍스트 저장: `save(role)`를 부르고, 결과를 지휘 프로세스로 보냅니다.
  8. 정리: `teardown(role)`을 부릅니다.
  9. 원자료 쓰기: 기록 버퍼를 지휘 프로세스로 보내거나 파일로 씁니다.
- **FR-RUN-3 (필수):** 위 1번부터 5번까지는 측정 구간 밖입니다. 다만 셋업의 시간과 메모리는 "셋업 단계"로 따로 기록합니다.
- **FR-RUN-4 (필수):** 프레임워크는 `WantRead`나 `WantWrite`를 받으면, 라이브러리 호출 밖에서 소켓이 읽기나 쓰기 가능해질 때까지 기다린 뒤 같은 함수를 다시 부릅니다. 기다림에는 `poll()` 또는 그와 같은 기능을 씁니다.

### 4.2 TCP와 지휘용 통로

- **FR-RUN-5 (필수):** TCP 연결이 준비되었다고 보는 조건은 세 가지입니다. `TCP_INFO`로 본 상태가 ESTABLISHED이고, 읽지 않은 바이트가 0이고, 설정 프로필이 정한 소켓 옵션이 실제로 걸려 있어야 합니다. 셋 가운데 하나라도 아니면 그 측정은 무효입니다.
- **FR-RUN-6 (필수):** 프레임워크의 신호와 데이터(준비 신호, 측정 번호, 연결 번호, 컨텍스트, 원자료)는 측정하는 TCP 연결로 보내지 않습니다. 지휘용 통로는 별도의 파이프나 유닉스 도메인 소켓을 씁니다.
- **FR-RUN-7 (필수):** 격리는 셋업과 TCP 준비가 끝난 뒤에 겁니다. 격리 뒤에 새 소켓을 만들려 하면 실패해야 합니다. 라이브러리가 선언한 스레드가 있다면 그것이 동작하도록 조정하고, 조정한 내용을 기록합니다.
- **FR-RUN-8 (필수):** 지휘 프로세스는 한쪽 역할이 실패하거나 제한 시간을 넘기면 다른 쪽을 멈추고, 그 측정을 무효로 기록합니다. 제한 시간의 기본값은 10초입니다.

### 4.3 반복과 순서

- **FR-RUN-9 (필수):** 설정 하나당 측정 횟수의 기본값은 1,000번입니다. 1,000번을 다시 세 묶음으로 나눠, 지휘 프로세스를 따로 세 번 실행합니다. 묶음 사이의 흔들림을 보려는 것입니다.
- **FR-RUN-10 (필수):** 여러 설정을 비교할 때는 설정을 섞어 번갈아 실행합니다. 설정 하나를 몰아서 다 돌린 뒤 다음 설정을 돌리지 않습니다. 섞는 순서는 기록된 씨앗으로 정해, 다시 만들 수 있게 합니다.
- **FR-RUN-11 (필수):** 실행 모드는 셋을 따로 둡니다. 한 번의 측정에서 서로 섞지 않습니다.
  - **시간 모드:** 시간, CPU 시간, 사이클, 명령어, 바이트를 잽니다. 할당 함수 교체와 스택 칠하기는 하지 않습니다.
  - **메모리 모드:** 힙과 스택을 잽니다. 시간 값은 기록하되 결과로 쓰지 않습니다.
  - **추적 모드:** 시스템 호출 추적, 패킷 캡처 같은 깊은 관측을 합니다. 검증 실험에만 씁니다.
- **FR-RUN-12 (필수):** 출발 상태는 시나리오로 정하고 기록합니다.
  - **차가운 쪽에 가까운 상태(기본):** 새 프로세스의 첫 연결을 잽니다. 선택으로, 측정 직전에 마지막 단계 캐시보다 큰 배열을 훑어 캐시를 밀어낼 수 있습니다.
  - **따뜻한 상태:** 같은 프로세스에서 데우기용 연결을 먼저 돌린 뒤 다음 연결을 잽니다.
  - **컨텍스트 상태:** 앞 측정이 남긴 컨텍스트를 넣은 상태입니다. 반복 측정에서는 한 번 만든 저장본을 매번 똑같이 넣습니다.

## 5. 사건 (FR-EVT)

### 5.1 사건 목록

- **FR-EVT-1 (필수):** 프레임워크는 다음 사건을 기록해야 합니다. 사건마다 시각과, 그 순간의 계측값(8절)을 붙입니다.

| 사건 | 언제 | 관측 위치 | 수준 |
|---|---|---|---|
| `SETUP_BEGIN`, `SETUP_END` | `setup()` 호출의 앞과 뒤 | 구현체 경계 | L0 |
| `TCP_READY` | TCP 확인이 끝난 때 | 프레임워크 | L0 |
| `OPEN_BEGIN`, `OPEN_END` | `open()` 호출의 앞과 뒤 | 구현체 경계 | L0 |
| `CALL_BEGIN`, `CALL_END` | 그 밖의 계약 함수 호출의 앞과 뒤입니다. 함수 이름과 돌려준 값을 붙입니다. | 구현체 경계 | L0 |
| `IO_SEND_ENTER`, `IO_SEND_RETURN` | 송신 함수의 진입과 반환입니다. 요청한 길이, 실제로 보낸 길이, 스트림 안의 위치를 붙입니다. | 구현체 경계 | L0 |
| `IO_RECV_ENTER`, `IO_RECV_RETURN` | 수신 함수의 진입과 반환입니다. 요청한 길이, 실제로 받은 길이, 스트림 안의 위치를 붙입니다. | 구현체 경계 | L0 |
| `WAIT_BEGIN`, `WAIT_END` | 프레임워크가 읽기나 쓰기 가능을 기다린 앞과 뒤입니다. 무엇을 기다렸는지 붙입니다. | 프레임워크 | L0 |
| `KERNEL_RX` | 받은 바이트가 커널에 도착한 시각입니다. 바이트 범위를 붙입니다. | 커널 | L1 |
| `KERNEL_TX_SCHED`, `KERNEL_TX_SND`, `KERNEL_TX_ACK` | 보낸 바이트가 커널의 대기열에 들어간 때, 장치로 넘어간 때, 상대가 받았다고 확인한 때입니다. 바이트 범위를 붙입니다. | 커널 | L1 |
| `NIC_RX`, `NIC_TX` | 네트워크 카드의 하드웨어 시각입니다. | NIC | L2 |
| `SYSCALL_ENTER`, `SYSCALL_EXIT` | 시스템 호출의 진입과 반환입니다. 추적 모드에서만 기록합니다. | 시스템 호출 경계 | L3 |
| `LIB_HOOK` | 라이브러리가 주는 콜백(메시지 알림, 인증서 검증 콜백 등)이 불린 때입니다. | 라이브러리 내부 | L3 |
| `PACKET` | 패킷 캡처에서 본 패킷입니다. 추적 모드에서만 기록합니다. | 선로 또는 캡처 지점 | L3 |
| `CLOSE_BEGIN`, `CLOSE_END` | `close()` 호출의 앞과 뒤입니다. | 구현체 경계 | L0 |
| `SAVE` | `save()`가 돌려준 컨텍스트의 크기입니다. | 프레임워크 | L0 |

- **FR-EVT-2 (필수):** 받은 길이가 0인 수신, 그리고 "지금은 받을 것이 없다"는 반환도 사건으로 기록합니다. 다시 시도한 횟수를 셀 수 있어야 하기 때문입니다.
- **FR-EVT-3 (필수):** 스트림 안의 위치는 방향마다 0부터 시작하는 바이트 위치입니다. 이 위치로 송수신 사건, 커널 시각, 메시지(16절)를 서로 이어 붙입니다.
- **FR-EVT-4 (필수):** 메시지 종류는 측정 중에 판단하지 않습니다. 측정이 끝난 뒤 키 로그 해석기(16절)가 바이트 위치로 붙입니다.

### 5.2 역할별 측정 구간의 시작과 끝

- **FR-EVT-5 (필수):** 역할별 측정 구간의 시작과 끝은 다음 사건으로 정합니다. 관측 수준마다 쓰는 사건이 다르며, 어느 사건을 썼는지 결과에 붙입니다.

| 역할 | 시작 | 끝 |
|---|---|---|
| 클라이언트 (L0) | 그 연결의 첫 `handshake_step` 호출의 `CALL_BEGIN`입니다. ClientHello 조립이 이 호출 안에서 시작된다고 봅니다. | 퐁의 마지막 평문 바이트를 돌려준 `app_recv` 호출의 `CALL_END`입니다. |
| 서버 (L0) | ClientHello의 첫 바이트를 받은 `IO_RECV_RETURN`입니다. | 퐁의 마지막 바이트를 보낸 `IO_SEND_RETURN`입니다. |
| 서버 (L1 이상) | ClientHello의 첫 바이트에 대한 `KERNEL_RX`입니다. | 퐁의 마지막 바이트에 대한 `KERNEL_TX_SND`입니다. |

- **FR-EVT-6 (필수):** `open()`에서 한 일은 측정 구간 밖이지만 버리지 않습니다. "핸드셰이크 앞의 일"로 따로 보고합니다. 구현체가 일을 `open()`으로 옮겨도 그 일이 기록에서 사라지지 않게 하려는 것입니다.
- **FR-EVT-7 (필수):** 각 엔드포인트의 핸드셰이크 완료 사건도 따로 보고합니다. 클라이언트와 서버 모두 `handshake_step`이 `Done`을 돌려준 `CALL_END`입니다.

## 6. 토막 (FR-SEG)

### 6.1 토막의 종류

- **FR-SEG-1 (필수):** 한 역할, 한 연결의 시간축은 다음 네 종류의 토막으로 빈틈없이, 겹침 없이 나뉘어야 합니다.

| 토막 | 정의 | 누구의 몫 |
|---|---|---|
| **연산 토막** | 라이브러리 호출 안에서, 송수신 함수 밖에 있는 구간입니다. 예를 들어 `CALL_BEGIN`부터 첫 `IO_*_ENTER`까지, `IO_*_RETURN`부터 다음 `IO_*_ENTER`까지, 마지막 `IO_*_RETURN`부터 `CALL_END`까지입니다. | 구현체 |
| **입출력 토막** | 송수신 함수 안의 구간입니다. 즉 `IO_*_ENTER`부터 `IO_*_RETURN`까지입니다. | 프레임워크와 커널 |
| **대기 토막** | `WAIT_BEGIN`부터 `WAIT_END`까지입니다. | 상대와 네트워크 |
| **틈 토막** | 라이브러리 호출 밖이면서 기다림도 아닌 구간입니다. 예를 들어 `CALL_END`부터 `WAIT_BEGIN`까지입니다. | 프레임워크 자신 |

- **FR-SEG-2 (필수):** 프레임워크는 측정이 끝날 때마다 네 종류 토막의 길이 합이 측정 구간의 길이와 같은지 확인해야 합니다. 같지 않으면 프레임워크의 결함이므로 그 측정을 무효로 하고 원인을 기록합니다.
- **FR-SEG-3 (필수):** 틈 토막은 프레임워크의 비용입니다. 틈 토막의 합은 결과와 함께 보고합니다.

### 6.2 토막 이름

- **FR-SEG-4 (필수):** 연산 토막에는 "무엇을 받은 뒤 무엇을 보내기 전까지"라는 이름을 원자료에서 자동으로 붙입니다. 이름은 해석기가 붙인 메시지 종류(16절)로 만듭니다.
  - 예: 클라이언트의 "서버 흐름(ServerHello에서 Finished)을 받은 뒤부터 클라이언트 Finished를 보내기 전까지"
  - 예: 서버의 "ClientHello를 받은 뒤부터 ServerHello를 보내기 전까지"
- **FR-SEG-5 (필수):** 한 연산 토막 안에서 메시지 여러 개가 처리되거나 만들어졌다면, 토막 이름에 그 메시지들을 모두 적고 "묶음"으로 표시합니다. 메시지별로 나누어 보고하지 않습니다.

### 6.3 쪼개는 깊이

- **FR-SEG-6 (필수):** 프레임워크가 모든 구현체에 대해 보장하는 가장 작은 단위는 L0 토막입니다. 즉 라이브러리 호출 경계와 송수신 함수 경계로 나뉜 토막입니다.
- **FR-SEG-7 (선택):** 라이브러리 내부를 더 나누는 일(L3: 라이브러리 콜백, 함수 탐침)은 라이브러리 하나를 들여다보는 용도입니다. 그 결과는 라이브러리끼리 비교하는 표에 넣지 않습니다.
- **FR-SEG-8 (필수):** 라이브러리끼리 비교할 때는 두 라이브러리가 모두 도달한 관측 수준의 토막만 씁니다.

## 7. 관측 수준 (FR-LVL)

- **FR-LVL-1 (필수):** 관측 수준은 다음과 같이 정합니다. 높은 수준은 낮은 수준을 모두 포함합니다.

| 수준 | 얻는 것 | 조건 |
|---|---|---|
| L0 | 라이브러리 호출 경계, 송수신 함수 경계, 대기 경계 | 송수신 함수 방식으로 붙인 모든 구현체 |
| L1 | L0과 커널의 소프트웨어 송수신 시각 | 커널이 `SO_TIMESTAMPING`의 소프트웨어 시각을 지원할 때 |
| L2 | L1과 네트워크 카드의 하드웨어 시각 | 네트워크 카드와 드라이버가 하드웨어 시각을 지원하고, 실제 네트워크 카드를 거칠 때 |
| L3 | 시스템 호출 추적, 라이브러리 콜백, 패킷 캡처 | 추적 모드, 그리고 필요한 권한이 있을 때 |

- **FR-LVL-2 (필수):** 호환 방식(소켓 직접 사용)으로 붙인 구현체는 송수신 함수 경계를 얻지 못합니다. 그 대신 시스템 호출 경계를 쓰며, 수준 이름에 "호환"을 붙여 L0과 섞이지 않게 합니다.
- **FR-LVL-3 (필수):** 측정마다 실제로 얻은 수준을 원자료에 기록합니다. 계획한 수준과 실제 수준이 다르면 실제 수준을 씁니다.
- **FR-LVL-4 (필수):** 같은 컴퓨터 안의 연결(127.0.0.1)에서는 L2를 얻을 수 없습니다. 이것을 "실패"가 아니라 "해당 없음"으로 기록합니다.

## 8. 계측값 (FR-MET)

### 8.1 사건마다 붙이는 값 (시간 모드)

- **FR-MET-1 (필수):** 사건마다 다음 값을 붙입니다.

| 값 | 얻는 방법 | 단위 |
|---|---|---|
| 단조 시각 | `clock_gettime(CLOCK_MONOTONIC)` | 나노초 |
| 스레드 CPU 시간 | `clock_gettime(CLOCK_THREAD_CPUTIME_ID)` | 나노초 |
| 사이클 수 | `perf_event_open()`으로 연 스레드 단위 카운터 | 사이클 |
| 명령어 수 | 위와 같음 | 개 |

- **FR-MET-2 (필수):** 사이클과 명령어는 기본으로 사용자 공간만 셉니다. 커널 실행까지 센 값은 선택 사항이며, 섞지 않고 별도 항목으로 기록합니다.
- **FR-MET-3 (필수):** 성능 카운터의 `time_enabled`와 `time_running`을 측정마다 기록합니다. 둘이 다르면, 즉 카운터가 다른 측정과 번갈아 쓰였다면 그 측정의 사이클과 명령어 값에 "불완전"을 붙이고 요약에서 뺍니다.
- **FR-MET-4 (필수):** 한 사건에서 값을 읽는 순서를 고정합니다. 기본 순서는 사이클, 명령어, 스레드 CPU 시간, 단조 시각입니다. 순서가 바뀌면 보정값(14절)도 다시 구합니다.

### 8.2 시계 맞추기

- **FR-MET-5 (필수):** 커널 시각이 어느 시계 기준인지 계측 도구 점검(13절)에서 확인합니다. 리눅스의 소프트웨어 송수신 시각은 실제 시각 시계(`CLOCK_REALTIME`) 기준으로 알려져 있습니다.
- **FR-MET-6 (필수):** 사용자 공간 시각과 커널 시각을 함께 쓸 때는, 프로세스 시작과 끝에 두 시계를 짝지어 읽어 둔 값으로 바꿉니다. 바꾸지 않은 두 시계의 값을 서로 빼면 안 됩니다.
- **FR-MET-7 (권장):** 측정하는 동안 시각 보정(NTP 등)을 멈춥니다. 멈추지 못했다면 그 사실을 기록합니다.

### 8.3 메모리 (메모리 모드)

- **FR-MET-8 (필수):** 힙은 할당 함수를 바꿔 끼워 셉니다. 사건마다 다음을 기록합니다.
  - 그 순간 살아 있는 바이트
  - 앞 사건부터 이 사건까지의 최고치
  - 할당 횟수, 해제 횟수, 할당한 바이트 합
- **FR-MET-9 (필수):** 프레임워크 자신의 할당은 구현체의 할당과 섞지 않습니다. 계측 중에는 프레임워크가 할당하지 않는 것을 원칙으로 하고, 필요하면 미리 잡아 둔 메모리만 씁니다.
- **FR-MET-10 (필수):** 스택은 라이브러리 호출마다 그 호출이 쓴 최고 깊이를 잽니다. 호출 직전에 스택 영역을 정해진 값으로 칠하고, 호출 직후에 덮인 깊이를 셉니다. 칠하는 일은 호출 밖에서 합니다.
- **FR-MET-11 (필수):** 다음 메모리 값을 역할별로 보고합니다.
  - 셋업 최고치
  - 핸드셰이크 중 최고치
  - 핸드셰이크 완료 직후 살아 있는 바이트(세션 유지에 드는 양)
  - 연결을 닫은 뒤에도 살아 있는 바이트
  - 컨텍스트 크기(연결 사이에 남는 상태)
- **FR-MET-12 (필수):** 호출하는 쪽이 넘겨준 버퍼, 미리 자리를 잡아 둔 고정 메모리처럼 할당 함수로 잡히지 않는 메모리는 구현자가 선언하게 하고, 그 크기를 따로 적습니다. 할당 함수로 잡힌 값과 더하지 않습니다.
- **FR-MET-13 (선택):** 라이브러리와 구현 코드의 코드 크기(텍스트, 데이터, BSS 영역)를 빌드할 때 기록합니다.

### 8.4 바이트

- **FR-MET-14 (필수):** 송수신 함수에서 방향별로 실제 보낸 바이트와 받은 바이트를 셉니다. 이것은 TLS 레코드 층의 바이트입니다.
- **FR-MET-15 (필수):** 메시지별 바이트와 레코드별 바이트는 해석기가 붙입니다(16절). 레코드 머리와 암호화 부가 바이트도 따로 셉니다.
- **FR-MET-16 (선택):** 추적 모드에서는 패킷 캡처로 TCP 조각 수와 IP 층 바이트를 셉니다.

## 9. 원자료에서 계산하는 값 (FR-DER)

- **FR-DER-1 (필수):** 역할별로 측정 구간의 길이를 경과 시간, CPU 시간, 사이클, 명령어로 계산합니다.
- **FR-DER-2 (필수):** 역할별로 연산 토막의 합, 입출력 토막의 합, 대기 토막의 합, 틈 토막의 합을 계산합니다.
- **FR-DER-3 (필수):** 토막 이름(FR-SEG-4)마다 같은 값을 계산합니다.
- **FR-DER-4 (필수):** 수신 쪽에서는 세 시각을 구별해 계산합니다.
  - 바이트가 커널에 도착한 때(`KERNEL_RX`, L1 이상)
  - 라이브러리가 바이트를 요구한 때(`IO_RECV_ENTER`)
  - 바이트를 라이브러리에 넘긴 때(`IO_RECV_RETURN`)

  첫째 시각이 둘째보다 앞서면, 그 차이를 "엔드포인트가 바빠서 늦게 가져간 시간"으로 따로 보고합니다.
- **FR-DER-5 (필수):** 다른 논문의 정의로 다시 계산하는 기능을 둡니다. 최소한 "클라이언트가 ClientHello를 보낸 때(첫 바이트의 `IO_SEND_RETURN`)부터 클라이언트가 Finished를 보낸 때까지"를 계산합니다.
- **FR-DER-6 (필수):** 두 역할을 짝지은 계산은 같은 연결끼리 먼저 하고, 그 뒤에 분포를 구합니다. 분포끼리 빼지 않습니다. 예를 들어 "클라이언트가 서버 흐름을 기다린 시간에서, 서버가 ClientHello를 받고 서버 흐름을 보내기까지 걸린 시간을 뺀 값"이 그렇습니다. 이 값은 "두 엔드포인트의 관측 지점 사이에서 쓴 시간"이라고 부르며, "순수한 네트워크 시간"이라고 부르지 않습니다.
- **FR-DER-7 (필수):** 다시 시도한 횟수를 계산합니다. `WantRead`와 `WantWrite`의 횟수, 받은 것이 없었던 수신의 횟수, 일부만 보낸 송신의 횟수입니다.

## 10. 설정 프로필 (FR-CFG)

- **FR-CFG-1 (필수):** 설정 프로필은 다음을 반드시 명시합니다. 라이브러리의 기본값에 맡기지 않습니다.

| 항목 | 내용 |
|---|---|
| 버전 | TLS 1.3만 허용합니다. |
| 암호 방식 | `TLS_AES_128_GCM_SHA256` 하나로 고정합니다. 다른 암호군이나 후보 목록은 허용하지 않습니다. |
| 키 교환 그룹 | 예: `x25519`. 클라이언트가 보내는 키 공유 값의 그룹과 서버가 받는 그룹이 같아야 합니다. 그래야 HelloRetryRequest가 생기지 않습니다. |
| 서명 방식과 인증서 체인 | 시험용 인증서 체계(M4)에서 고릅니다. 체인 길이와 서명 방식을 적습니다. |
| 상호 인증 | 켬 또는 끔 |
| 티켓 장수 | 기본 0 |
| 가짜 ChangeCipherSpec | 켬 또는 끔. 라이브러리 기본값을 확인하고, 프로필에서 명시적으로 정합니다. |
| 서버 이름 표시(SNI) | 보낼 이름 |
| 응용 데이터 | 핑과 퐁의 길이. 기본은 각각 32바이트입니다. |
| 소켓 옵션 | 지연 없이 보내기(`TCP_NODELAY`)의 켬과 끔, 송수신 버퍼 크기. 기본값은 아직 정하지 않았으며(20절), 정하면 모든 구현체에 같게 적용합니다. |
| 기법 | 적용한 경량화 기법과 그 설정 |

- **FR-CFG-2 (필수):** 프로필은 파일로 저장하고, 원자료의 모든 측정에 프로필의 이름과 해시값을 붙입니다.
- **FR-CFG-3 (필수):** 실제로 협상된 값(`negotiated()`와 해석기의 결과)을 프로필과 비교해 원자료에 남깁니다. 둘이 다르면 그 측정은 무효입니다. 이것은 꼼수 방지가 아니라, 무엇을 쟀는지 남기는 기록입니다.

## 11. 무효 판정 (FR-VAL)

- **FR-VAL-1 (필수):** 다음 가운데 하나라도 해당하면 그 측정은 무효입니다. 원자료에 이유와 함께 남기고, 요약에서는 뺍니다.
  1. TCP 준비 조건(FR-RUN-5)을 만족하지 못했습니다.
  2. `handshake_step`이 `Failed`를 돌려주었습니다.
  3. 검증 결과가 `Failed`이거나, 클라이언트가 `Passed`가 아닌 값을 돌려주었습니다.
  4. 협상된 값이 프로필과 다릅니다(FR-CFG-3).
  5. 범위 밖의 메시지(FR-SCOPE-2)가 해석기에서 발견되었습니다.
  6. 핑과 퐁의 평문이 보낸 것과 다릅니다.
  7. 제한 시간을 넘겼거나, 한쪽 역할이 비정상으로 끝났습니다.
  8. 기록 버퍼가 넘쳤습니다. 넘친 기록을 조용히 버리면 안 됩니다.
  9. 토막의 합이 측정 구간과 맞지 않습니다(FR-SEG-2).
- **FR-VAL-2 (필수):** 다음은 무효가 아니라 "불완전"으로 표시합니다. 해당 값만 요약에서 빼고, 나머지 값은 씁니다.
  - 성능 카운터가 번갈아 쓰였습니다(FR-MET-3).
  - 커널 시각 일부가 빠졌습니다.
- **FR-VAL-3 (필수):** 설정마다 유효한 측정 수, 무효인 측정 수와 그 이유별 수, 불완전한 측정 수를 보고합니다.
- **FR-VAL-4 (필수):** 무효인 측정은 다시 돌려 채우되, 다시 돌린 횟수도 보고합니다. 무효 비율이 1%를 넘으면 그 설정의 결과에 경고를 붙입니다.

## 12. 측정 환경 (FR-ENV)

- **FR-ENV-1 (필수):** 클라이언트, 서버, 지휘 프로세스를 서로 다른 물리 코어에 고정합니다. 같은 물리 코어를 나눠 쓰는 하이퍼스레드 형제 코어는 쓰지 않습니다.
- **FR-ENV-2 (필수):** 클럭 자동 상승(Turbo Boost 등)을 끄고, 주파수 조절 정책을 `performance`로 둡니다. 할 수 없는 환경이면 그 사실을 기록하고, 결과에 경고를 붙입니다.
- **FR-ENV-3 (권장):** 측정하는 동안 다른 일이 없는 컴퓨터를 씁니다. 측정 전후의 부하 평균을 기록합니다.
- **FR-ENV-4 (필수):** 측정 환경 정보를 모든 원자료에 붙입니다. CPU 모델, 코어 배치, 주파수 정책, 커널 판, 컴파일러와 옵션, 라이브러리 판과 빌드 옵션, WSL2인지 여부가 들어갑니다.
- **FR-ENV-5 (필수):** WSL2에서 잰 값과 일반 리눅스에서 잰 값은 섞지 않습니다. 논문의 최종 수치는 일반 리눅스에서 잽니다(권장). WSL2는 개발과 기능 시험에 씁니다.

---

## 13. 계측 도구 점검 (FR-CAP)

- **FR-CAP-1 (필수):** 측정 전에 다음을 확인하고 결과를 기록하는 부품을 둡니다. 결과는 원자료에도 붙이고, 사람이 읽을 수 있는 보고로도 냅니다.
  - 성능 카운터를 열 수 있는가, 사용자 공간만인가 커널도 포함인가, 카운터를 몇 개 동시에 쓸 수 있는가
  - 단조 시계와 스레드 CPU 시계의 해상도와 한 번 읽는 비용
  - 커널 송신 시각(대기열, 장치, 확인 응답)과 수신 시각의 지원 여부, 그리고 그 시계의 기준
  - 네트워크 카드의 하드웨어 시각 지원 여부
  - 시스템 호출 추적(eBPF)과 패킷 캡처의 권한
  - 클럭 자동 조절 상태와 주파수 정책
  - 코어 고정 가능 여부와 하이퍼스레드 구성
  - 구현체의 선언(FR-CON-6): 송수신 함수, 할당 함수, 키 로그 지원 여부
- **FR-CAP-2 (필수):** 점검 결과로 이번 측정의 목표 관측 수준을 정합니다. 목표 수준을 얻지 못하면 낮은 수준으로 진행하되, 실제 수준을 기록합니다(FR-LVL-3).

---

## 14. 계측 비용 보정 (FR-CAL)

- **FR-CAL-1 (필수):** 빈 토막을 재서 계측의 직접 비용을 구합니다. 사건 기록을 연달아 두 번 해서 그 차이를 시간, CPU 시간, 사이클, 명령어로 잽니다. 측정 프로세스마다 시작할 때 일정 횟수 재고, 그 분포를 기록합니다.
- **FR-CAL-2 (필수):** 보정값을 뺀 값과 빼지 않은 값을 모두 원자료에서 계산할 수 있어야 합니다. 보고에는 어느 쪽인지 밝힙니다.
- **FR-CAL-3 (필수):** 계측이 측정 대상을 흔드는 효과는 계측 수준을 바꿔 가며 확인합니다(검증 실험). 비교하는 것은 처음부터 끝까지의 시간 분포와 패킷 캡처의 모양(패킷 수, 크기, 순서)입니다. 차이가 있으면 결과와 함께 보고합니다.

---

## 15. 원자료 (FR-REC)

- **FR-REC-1 (필수):** 측정 중의 기록은 측정 전에 미리 잡아 둔 고정 크기 버퍼에 씁니다. 측정 중에 파일을 쓰거나 메모리를 잡지 않습니다.
- **FR-REC-2 (필수):** 원자료는 한 줄에 사건 하나를 쓰는 텍스트 형식으로 저장합니다. 모든 줄에 다음을 붙입니다.
  - 형식 판 번호
  - 측정 번호, 묶음 번호, 역할, 연결 번호, 사건 번호
  - 사건 종류와 관측 위치
  - 계측값
  - 설정 프로필 해시와 환경 정보 해시
- **FR-REC-3 (필수):** 측정마다 머리 줄을 하나 둡니다. 여기에 프로필 전체, 환경 정보 전체, 계측 도구 점검 결과, 실제 관측 수준, 출발 상태, 보정값을 담습니다.
- **FR-REC-4 (필수):** 실패와 무효인 측정도 같은 형식으로 남깁니다. 지우지 않습니다.
- **FR-REC-5 (필수):** 원자료 형식 설명서(`docs/record-format.md`)를 두고, 형식이 바뀌면 판 번호를 올립니다.
- **FR-REC-6 (필수):** 키 로그와 전송된 바이트(해석기에 필요한 것)는 측정이 끝난 뒤 원자료와 같은 측정 번호로 저장합니다. 시험용 인증서와 키만 쓰므로 비밀값을 남겨도 됩니다.

---

## 16. 키 로그 해석기 (FR-INT)

- **FR-INT-1 (필수):** 해석기는 측정이 끝난 뒤에 돕니다. 측정 중에는 아무 해석도 하지 않습니다.
- **FR-INT-2 (필수):** 해석기는 방향별로 저장된 바이트 스트림을 TLS 레코드로 나누고, 키 로그의 비밀값으로 보호된 레코드를 풀어 안의 메시지 종류를 알아냅니다.
- **FR-INT-3 (필수):** 결과는 메시지마다 다음을 담습니다. 방향, 종류, 메시지가 차지한 바이트 범위, 그것을 담은 레코드 번호, 레코드 머리와 부가 바이트입니다.
- **FR-INT-4 (필수):** 가짜 ChangeCipherSpec, NewSessionTicket, 응용 데이터, 경고를 구별합니다.
- **FR-INT-5 (필수):** 모르는 메시지 종류를 만나면 멈추지 않고 "모르는 종류, 몇 바이트"로 기록합니다.
- **FR-INT-6 (필수):** 해석기의 결과로 송수신 사건과 연산 토막에 메시지 이름을 붙입니다(FR-SEG-4).
- **FR-INT-7 (필수):** 기법이 키를 만드는 과정을 바꿔 풀 수 없으면, 풀지 못했다고 기록하고 토막에 메시지 이름 대신 바이트 범위만 붙입니다.

---

## 17. 통계와 보고 (FR-STAT)

- **FR-STAT-1 (필수):** 설정, 역할, 토막 이름, 계측값마다 다음을 보고합니다.
  - 유효 측정 수
  - 안정화 사분위수 셋(StQ1, StQ2, StQ3). 정렬한 측정값에서 각각 1/8에서 3/8, 3/8에서 5/8, 5/8에서 7/8 구간의 평균입니다.
  - 최솟값과 최댓값
- **FR-STAT-2 (필수):** 분포 전체를 그림으로 남깁니다. 숫자 셋만으로 요약하지 않습니다.
- **FR-STAT-3 (필수):** 두 설정의 차이는 StQ2의 차이로 보고하고, 측정값을 다시 뽑아 만든 95% 신뢰 구간(부트스트랩)을 붙입니다. 신뢰 구간이 0을 포함하면 "이 측정으로는 구별할 수 없음"이라고 보고합니다.
- **FR-STAT-4 (필수):** 묶음(FR-RUN-9) 사이의 StQ2 차이를 보고합니다. 묶음 사이의 차이가 설정 사이의 차이보다 크면 경고를 붙입니다.
- **FR-STAT-5 (필수):** 결과는 역할별로 따로 보고합니다. 클라이언트와 서버의 값을 더해 하나로 만들지 않습니다.
- **FR-STAT-6 (필수):** 모든 표에 관측 수준, 출발 상태, 실행 모드, 보정 여부를 적습니다.

---

## 18. 받아들임 시험 (FR-TEST)

각 영역은 아래 시험을 통과해야 끝난 것으로 봅니다. 시험은 `tests/`의 별도 프로젝트에 두고, 20번 반복해도 늘 통과해야 합니다.

| 시험 | 확인하는 요구사항 | 방법 |
|---|---|---|
| 격리 | FR-RUN-7 | 격리 뒤에 소켓을 만들려 하면 실패하는지 봅니다. |
| 새 프로세스 | FR-RUN-1 | 측정마다 프로세스 번호가 다른지 봅니다. |
| 통로: 일부만 보내기와 받기 | FR-EVT-1, FR-EVT-3, FR-DER-7 | 알려진 바이트를 쪼개 보내고 합쳐 받는 시험용 구현으로, 바이트 위치와 다시 시도한 횟수가 맞는지 봅니다. |
| 토막의 합 | FR-SEG-2 | mock과 실제 라이브러리 모두에서 네 종류 토막의 합이 측정 구간과 같은지 봅니다. |
| 무효 판정 | FR-VAL-1 | 각 무효 조건을 시험용 구현으로 일으켜, 이유가 맞게 기록되는지 봅니다. |
| 컨텍스트 | FR-CON-1, FR-RUN-12 | 컨텍스트가 있을 때와 없을 때 출력이 달라지고, 크기가 기록되는지 봅니다. |
| 협상 값 | FR-CFG-3 | 프로필과 다른 그룹을 쓰도록 일부러 설정해 무효가 되는지 봅니다. |
| 해석기 | FR-INT-2부터 FR-INT-5 | OpenSSL의 메시지 알림 콜백 결과와 해석기 결과가 일치하는지 봅니다. |
| 시계 | FR-MET-5, FR-MET-6 | 커널 시각과 사용자 공간 시각을 바꾼 결과의 순서가 인과에 맞는지 봅니다. 예를 들어 같은 바이트의 `KERNEL_RX`가 `IO_RECV_RETURN`보다 늦으면 안 됩니다. |
| 보정 | FR-CAL-1 | 빈 토막의 분포가 기록되는지 봅니다. |
| 원자료 | FR-REC-2부터 FR-REC-5 | 원자료만으로 요약을 다시 만들어 같은 값이 나오는지 봅니다. |
| 모듈 경계 | FR-MOD-2부터 FR-MOD-7 | 부품 라이브러리를 하나씩 따로 빌드할 수 있는지 봅니다. CMake의 의존 그래프(`cmake --graphviz`)에 순환이 없는지 봅니다. `src/`의 파일이 다른 부품의 내부 헤더를 포함하지 않는지, 프레임워크 코드에 라이브러리 이름 분기가 없는지 검사 스크립트로 확인합니다. |
| 부품 단독 시험 | FR-MOD-14 | `tests/<부품>/`의 시험이 그 부품 라이브러리만 연결해서 통과하는지 봅니다. |

## 19. 코드 구조와 모듈화 (FR-MOD)

코드는 가능한 한 유지보수가 쉽도록 모듈로 나눕니다. 이 절의 요구사항은 그것을 확인할 수 있는 규칙으로 바꾼 것입니다.

### 19.1 부품과 경계

- **FR-MOD-1 (필수):** 프레임워크는 부품으로 나눕니다. 부품 하나는 `src/<부품>/` 폴더 하나이며, 그 안에 `.cpp`와 내부용 `.hpp`를 함께 둡니다. 예상하는 부품은 다음과 같습니다. 부품 폴더는 그 부품의 첫 코드가 생길 때 만듭니다.

| 부품 | 맡는 일 | 맡지 않는 일 |
|---|---|---|
| `lifecycle` | 지휘 프로세스, 역할 프로세스, 라이프사이클 순서, 무효 판정 | 소켓 다루기, 계측값 읽기 |
| `transport` | TCP 준비와 확인, 송수신 함수, 대기 | 무엇을 기록할지 정하기 |
| `control` | 지휘용 통로(준비 신호, 번호, 컨텍스트, 원자료 전달) | 측정하는 TCP 연결 |
| `measure` | 시계, 성능 카운터, 할당 함수, 스택 칠하기, 보정 | 원자료 형식 |
| `record` | 미리 잡은 기록 버퍼, 원자료 쓰기 | 해석과 요약 |
| `capability` | 계측 도구 점검 | 측정 |
| `interpret` | 키 로그 해석기 | 측정 |
| `report` | 요약기, 다른 정의로 다시 계산하기, 그림 | 측정 |

- **FR-MOD-2 (필수):** 부품마다 CMake 라이브러리 대상 하나를 둡니다. 부품 사이의 의존은 `target_link_libraries`로만 드러냅니다.
- **FR-MOD-3 (필수):** 부품은 다른 부품의 공개 헤더 하나만 씁니다. 다른 부품의 내부 헤더를 포함하지 않습니다.
- **FR-MOD-4 (필수):** 부품 사이에 순환 의존이 없어야 합니다. `lifecycle`은 다른 부품을 쓸 수 있지만, 다른 부품은 `lifecycle`을 쓰지 않습니다. `transport`, `control`, `measure`, `record`는 서로를 쓰지 않는 것을 원칙으로 하고, 꼭 필요하면 그 이유를 `docs/architecture.md`에 적습니다.

### 19.2 계약과 구현의 분리

- **FR-MOD-5 (필수):** 계약 헤더(`include/turtle/`)는 프레임워크 내부 헤더를 포함하지 않습니다.
- **FR-MOD-6 (필수):** 구현자 코드(`implementations/<이름>/`)는 `include/turtle/`만 볼 수 있게 빌드합니다. `src/`의 헤더를 볼 수 없어야 합니다.
- **FR-MOD-7 (필수):** 라이브러리마다 다른 처리는 `implementations/<이름>/` 안에만 둡니다. 프레임워크 코드에는 라이브러리 이름으로 갈라지는 코드가 없어야 합니다. 예를 들어 "OpenSSL이면 이렇게 한다" 같은 분기가 그렇습니다.

### 19.3 측정 경로의 분리

- **FR-MOD-8 (필수):** 측정하는 구간 안에서 도는 코드는 `transport`의 송수신 함수, `measure`의 값 읽기, `record`의 버퍼 쓰기뿐이어야 합니다. 이 경로의 코드는 짧고 단순하게 유지합니다.
- **FR-MOD-9 (필수):** 해석기(`interpret`)와 요약기(`report`)는 측정 프로그램과 별도의 실행 파일로 둡니다. 분석 코드를 고쳐도 측정 프로그램이 바뀌지 않게 하려는 것입니다.

### 19.4 바꿔 끼우는 부품

- **FR-MOD-10 (필수):** 바꿔 끼울 수 있는 부품은 작은 인터페이스 하나 뒤에 둡니다. 예를 들어 통로(메모리 위 통로와 TCP), 계측(카운터 종류), 출발 상태가 있습니다.
- **FR-MOD-11 (필수):** 인터페이스는 두 번째 구현이 실제로 생길 때 만듭니다. 구현이 하나뿐인데 미리 인터페이스, 공장 함수, 설정 항목을 만들지 않습니다. 미리 만든 추상화는 유지보수를 오히려 어렵게 합니다.

### 19.5 설정, 설명, 시험

- **FR-MOD-12 (필수):** 포트, 제한 시간, 측정 횟수, 버퍼 크기 같은 값은 설정 프로필이나 실행 인자 한곳에서 읽습니다. 코드 곳곳에 숫자로 흩어 두지 않습니다.
- **FR-MOD-13 (필수):** 부품마다 무엇을 맡고 무엇을 맡지 않는지를 그 부품의 공개 헤더 첫머리에 짧게 적습니다. 부품 목록과 의존 관계는 `docs/architecture.md`에 그림이나 표로 둡니다.
- **FR-MOD-14 (필수):** 부품마다 그 부품만 연결해서 도는 시험을 `tests/<부품>/`에 둡니다. 다른 부품 전체를 띄우지 않고 그 부품을 시험할 수 있어야 합니다.
- **FR-MOD-15 (권장):** 파일 하나는 한 가지 일을 합니다. 파일이 500줄을 넘으면 나눌지 검토하고, 나누지 않았다면 그 이유를 적습니다.

## 20. 아직 정하지 않은 값

아래 값은 아직 정하지 않았습니다. 정하면 `docs/DECISIONS.md`에 적고 이 명세를 고칩니다.

- **지연 없이 보내기(`TCP_NODELAY`)의 기본값:** 켜면 계측 시간이 끼어들어도 패킷이 덜 합쳐지고, 끄면 라이브러리 기본 동작에 가깝습니다.
- **가짜 ChangeCipherSpec의 기본값**
- **설정 하나당 측정 횟수:** 기본 1,000번이 충분한지는 첫 결과의 분포를 보고 다시 정합니다.
- **캐시를 밀어내는 배열 훑기를 기본으로 할지**
- **모의 CA:** 이 명세에는 아직 들어 있지 않습니다. 설계 메모를 연구자가 확인한 뒤 영역 `FR-CA`로 더합니다.
- **호환 방식(소켓 직접 사용)의 시스템 호출 추적 방법:** eBPF를 기본 후보로 둡니다.
