# TURTLE review, 2026-10-15: defects, refactoring, and what is still missing

Scope: the tree at `ab7099b` (HEAD). Everything below was verified independently
on this machine: fresh build of source and tests with all three adapters,
73/73 tests passing once, and single-sample event timelines for
OpenSSL/OpenSSL, wolfSSL/wolfSSL, and Mbed TLS/Mbed TLS decoded with
`turtle-interpret`. All numbers quoted are WSL diagnostics from one sample
each. They are used only to show *structure*; none of them is a performance
claim.

This is a work order. Each item has an acceptance criterion. Do not widen
scope: no new research techniques, no robustness tests, no security claims.

## 0. Ground rules for every item

- Any change to what falls inside a measurement window is a change of the
  measured object. It needs a `docs/DECISIONS.md` entry, a test, and a note in
  `implementations/common/README.md` when it is adapter-specific.
- Keep client and server separate. Keep "unavailable" distinct from zero.
- Raw record schema stays additive. New fields are optional and old raw data
  must still interpret and report. If a field cannot be additive, bump the
  schema and keep the reader for schema 1.
- Before each commit: `REPEAT=20 JOBS=4 scripts/check.sh`, static checks, and
  an offline replay of the preserved raw data under `results/` producing a
  byte-identical `summary.json` wherever the change does not touch that
  output. Commit per section with Lore trailers.

## 1. Defects

### D1. wolfSSL generates the ECDHE key share outside the measurement window (highest priority)

`implementations/wolfssl/wolfssl_adapter.cpp` calls `wolfSSL_UseKeyShare(ssl,
WOLFSSL_ECC_SECP256R1)` inside `open()`. In wolfSSL 5.8.2,
`TLSX_KeyShare_Use()` calls `TLSX_KeyShare_GenKey()` immediately when no peer
data is supplied (`.deps/src/wolfssl-5.8.2-stable/src/tls.c`). The timelines
show it:

| adapter | OPEN segment, client | CALL_BEGIN to first send (ClientHello build) | OPEN segment, server |
|---|---:|---:|---:|
| OpenSSL 3.5.4 | 31 us | 100 us | 31 us |
| wolfSSL 5.8.2 | 310 us | 15 us | 298 us |
| Mbed TLS 3.6.4 | 16 us | 283 us | 15 us |

The primary window starts at the first handshake call, so the wolfSSL client
and server numbers exclude key generation while the other two adapters
include it. The three adapters do not measure the same object today.

Fix: remove the `open()`-time call. Either call it in `handshake_step()` on
the first invocation, before `wolfSSL_connect`/`wolfSSL_accept`, or set the
group list only (`wolfSSL_set_groups` or equivalent) and let wolfSSL generate
the share during the handshake. Prefer whichever keeps a single P-256 share
and no HelloRetryRequest.

Acceptance:
- No key-generation call remains in `open()` for any adapter. State for each
  adapter, in `implementations/common/README.md`, where key-share generation
  and certificate parsing happen relative to the window.
- Integration test for wolfSSL client and server: the decoded transcript has
  exactly one ServerHello, no HelloRetryRequest, and the negotiated group is
  secp256r1.
- Timeline re-run: wolfSSL OPEN is in the same order of magnitude as the other
  adapters, and its ClientHello build segment is no longer an order of
  magnitude smaller. Record the before/after timelines in
  `docs/validation.md`; do not add a timing assertion to CTest.

### D2. Framework copy work is charged to the library segment

In `Capture::observe` (`src/lifecycle/lifecycle.cpp`) the snapshot for an
IO return event is taken first; the stream copy (`append_bytes`) and the
KERNEL_RX event append run after it. Those costs therefore fall into the
following "computation" segment, i.e. they are attributed to the TLS library.
The amounts are small (sub-microsecond for handshake records) but the
attribution is wrong by construction, and it matters for the 2 to 4 us
segments such as EncryptedExtensions processing.

Fix: for returning observations, perform the stream copy before taking the
snapshot so that framework work lands in the "io" segment, which is already
defined as kernel plus framework. Keep the KERNEL_RX append after the
snapshot only if it is cheaper than a clock read; otherwise move it too.
Document the resulting definition of "io" and "computation" in
`docs/runtime.md`.

Acceptance: the partition identity (computation + io + wait + gap = elapsed)
still holds in all tests; `docs/runtime.md` states exactly which framework
work is inside "io"; the calibration section explains what remains
unaccounted (one clock read per event).

### D3. Message notifications carry no timestamps and exist only in trace mode

OpenSSL's `SSL_CTX_set_msg_callback` is connected, but the plaintext sink is
only fed when `trace_mode` is on and the record has no snapshot. In timing
mode the `*.plaintext.*` files are empty. So there is no library-side
message boundary at all in a timing run. This is not wrong, but the docs
imply more than exists. Resolution is item G2 below; until then, state in
`docs/record-format.md` that message notifications are a trace-mode oracle
without timing.

Acceptance: docs updated; no code change required for this item.

## 2. Refactoring (behavior preserving)

Only what is needed to host section 3 cleanly. Acceptance for every item:
73/73 tests, module-boundary check, static checks, and byte-identical offline
replay of the preserved raw data.

### R1. Split `src/lifecycle/lifecycle.cpp` by process role

964 lines still mix the director (sampling loop, attempt ledger, reaping,
network handoff) with the role child runtime (`Capture`, handshake loop,
window bookkeeping). Split into `director.cpp` and `role_runtime.cpp`, keep
`lookup_runtime.cpp` as is. No public header change.

### R2. Extract window and partition logic from `src/report/report.cpp`

The partition, the client ClientHello-to-Finished window, and the
observer-mode common window live inline in a 1,100-line file. Move them to
`report/window.cpp` with a small header. G1 and G3 are added there instead of
growing `report.cpp` further.

### R3. Keep `src/model/model.hpp` for the TLS model

`LookupConfig`, `NetworkHandoff`, `ServiceEventKind`, `AttemptStatus` and the
other lookup/netem types now sit next to the TLS event model. Move them to
`model/service.hpp` (same namespace). Core TLS code must not need to include
it. This also makes it obvious which types belong to the frozen M13/M14
scope.

## 3. Gaps that keep TURTLE from being a benchmark framework yet

### G1. Per-record attribution in the report (highest value for the paper)

The interpreter already annotates every IO event with the message names its
record range overlaps and a `bundled` flag (verified: the OpenSSL server's
single 1,249-byte send carries six names, `bundled=true`). The report does
not use it; it only emits an unlabeled segment list.

Add to each role's connection result a list of attributed library segments:

- `after_receive`: the computation segment that follows an IO_RECV_RETURN
  completing a record body, labeled with that record's message names.
- `before_send`: the computation segment that precedes an IO_SEND_ENTER,
  labeled with the names of the record(s) in that send.
- `bundled=true` on either side means "not attributable to one message";
  keep the segment, keep the names, never split the time across names.
- Segments with no IO on either side (first segment after CALL_BEGIN, segment
  before CALL_END) get labels `call_begin` and `call_end`.

What this makes visible, from the single-sample timelines (client role,
library segment after each received record, microseconds):

| after record | OpenSSL | wolfSSL | Mbed TLS |
|---|---:|---:|---:|
| ServerHello | 123 | 329 | 532 |
| EncryptedExtensions | 4 | 3 | 2 |
| Certificate | 198 | 454 | 1,501 |
| CertificateVerify | 52 | 199 | 719 |
| Finished (includes building own Finished) | 25 | 11 | 17 |

And on the server send side: OpenSSL writes the whole flight in one send, so
nothing is attributable; wolfSSL and Mbed TLS write per message but place
the work differently (wolfSSL does key derivation after sending ServerHello,
so its "before EncryptedExtensions" segment is 300 us while Mbed TLS puts
948 us before ServerHello). The report must therefore say, in its notes,
that attributed segments measure where the library schedules work, not the
intrinsic cost of a message, and that only flight-level sums are comparable
across libraries.

Acceptance:
- Unit test on synthetic events for all four label kinds and the bundled
  rule.
- Integration fixtures: OpenSSL server flight yields one `before_send` entry
  with six names and `bundled=true`; wolfSSL and Mbed TLS yield six separate
  entries; every client yields one `after_receive` entry per record.
- The attributed list is absent, with a reason, when the decoded file is
  missing or incomplete, and when the channel observer is off.
- Attributed segments never enter automatic comparison; they are
  per-connection evidence only.

### G2. Timestamped library message notifications as a declared, optional capability

Define an event kind `LIBRARY_MESSAGE` (direction, content type, handshake
type when known, length, full snapshot). Adapters that can emit it declare
`message_timestamps=true`. OpenSSL can (msg callback fires after a handshake
message is built and before it is written, and after it is read and before
it is processed). Check whether wolfSSL offers an equivalent callback; Mbed
TLS does not, and must declare false. Enable it with a profile switch, off by
default, and put the switch in the group key exactly like
`channel_observer`, because it adds work inside the window.

Acceptance: timing-mode run with the switch on records LIBRARY_MESSAGE
events for OpenSSL with monotonic and CPU snapshots; the decoder cross-checks
their type sequence against decoded records; reports with the switch on and
off never share a group; Mbed TLS runs with the switch on fail at setup with
a clear reason rather than silently recording nothing.

### G3. One table of measurement windows, symmetric for both roles

Today: primary window for both roles, a ClientHello-to-Finished-send window
for the client only, and the observer-mode common window. Add the server
counterpart (first ClientHello byte received to server Finished send return)
and write one table in `docs/runtime.md` listing every window with its start
event, end event, what it includes (tickets, CCS, application ping-pong), and
which roles have it. The paper needs this table verbatim.

Acceptance: server window implemented and tested on the three-library
fixtures; the table exists and every window name in `summary.json` appears
in it.

### G4. Pin and declare record-reading behavior

Per-record visibility on the receive side (G1) depends on each library
reading one record at a time: header, then body, then process. That is the
current default in all three, but it is not pinned. Set OpenSSL read-ahead
off explicitly, check the wolfSSL and Mbed TLS equivalents, and record the
setting in each adapter's Declaration.

Acceptance: Declaration has a `read_ahead` field per adapter; the
integration fixtures assert the header-then-body pattern (two recv returns
per record) for all three libraries.

### G5. Environment facts needed before physical-Linux runs

`capability.cpp` already records governor, boost/no_turbo, and cpuinfo. Add:
SMT sibling of every pinned CPU, with a warning when two roles share a
physical core or when a sibling is not idle; kernel version and
`perf_event_paranoid`; whether the perf group is user-only. Put the perf
scope into the Declaration/capabilities and into the group key.

Acceptance: environment JSON contains the new fields on this machine
(values may be "unavailable"); a unit test covers the shared-physical-core
warning.

### G6. Perf counters are user-space only; say so and make it a choice

`measure.cpp` sets `exclude_kernel=1`. The per-endpoint cycle count therefore
excludes kernel work in send/recv. That is a legitimate definition but it
must be declared, and a profile option should allow including the kernel
when `perf_event_paranoid` permits. Different settings never share a group.

Acceptance: capabilities and summary state `perf_scope: user` or
`user+kernel`; the option is honored or refused with a reason; group key
includes it.

### G7. Known limitations to state, not build now

- No two-host mode: every role runs on one host, including the namespace
  topology. The Raspberry Pi plan will need either a remote role runner or
  an explicit "same host, separate cores" caveat in the paper.
- No instrumentation-free baseline for the server role. The native socket
  path gives a comparable client window for OpenSSL only. Decide whether the
  paper reports the observer on/off difference as the overhead bound or
  builds a minimal external baseline; do not build anything until decided.
- Stack high-water, kernel transmit timestamps, eBPF: unsupported and
  declared. Leave as is.
- Lookup, Mock CA, and netem: frozen at the documented boundary. No new
  work.

## Appendix: how the timelines were produced

```sh
./build/turtle run --client openssl --server openssl \
  --profile examples/profiles/server-auth.json --pki pki/default \
  --samples 1 --no-affinity --output OUT
./build/turtle-interpret OUT/sample-000001/client.jsonl OUT/sample-000001/client.decoded.json
./build/turtle-interpret OUT/sample-000001/server.jsonl OUT/sample-000001/server.decoded.json
```

Then, per role, walk the `event` rows in sequence order, track whether the
cursor is inside a call, inside an IO callback, or inside a wait, and label
each inter-event interval accordingly; join IO events to decoded message
names through `event_annotations` (or by overlapping `stream_begin`/`stream_end`
with `record_stream_ranges`). A throwaway reference script that does exactly
this exists at
`/tmp/claude-1000/-home-kosh-TURTLE/055fa49c-d3ef-4508-909e-b130d5249187/scratchpad/timeline.py`;
treat it as a specification for G1, not as code to copy.
