# TURTLE의 `build.sh` 계약

**개발자는 자기 라이브러리를 어떻게 만드는지만 알려준다. 그 라이브러리로 TURTLE의 클라이언트와 서버를 만드는 일은 TURTLE이 맡는다.** 아래는 기본 제출 경로의 계약이다. 특정 소스 트리나 라이브러리 목록이 계약인 것이 아니다.

## 처음 연결하는 사람을 위한 요약

| 누가 | 준비하거나 수행할 일 |
|---|---|
| 개발자 | `implementations/`에 **원래 TLS 소스 폴더**, **실행 가능한 `build.sh`**, **`implementation.cpp`**를 둔다. 이미 쓰는 원본 빌드 방법을 그대로 호출한다. |
| `build.sh` | TURTLE이 준 빈 작업 경로에서 원본을 빌드해, 빈 설치 경로에 **그 구성의 헤더 + 공유 라이브러리 + 이를 소비하는 데 필요한 pkg-config 정보**를 설치한다. |
| TURTLE | 원본 빌드 완료 후 공통 [선언](../src/include/turtle/implementation.hpp)과 설치된 SDK로 `implementation.cpp`를 컴파일한다. 선택된 **하나의 목적 파일**로 프레임워크 소유의 client/server를 각각 링크한다. |
| 사용자 | 준비한 뒤 `./bench.sh` 한 번. 빌드만 확인하려면 `./bench.sh --build-only`. 두 실행 파일이 생기며 TLS 연결·doctor·성능 결과는 생기지 않는다. |

이용자는 별도의 서버 프로그램, CMake 타깃, 구현체 등록, 시스템 전역 설치를 준비할 필요가 없다. **예시를 보고 싶은 경우에만** [레시피 모음](examples/submissions/README.md)을 본다. 새 checkout의 [제출 폴더](../implementations/README.md)에는 편집 가능한 레시피와 7개 함수의 비활성 틀이 있다. 실제 TLS 구현은 들어 있지 않다. 예시를 쓸 때만 `tools/init-submission-example.sh NAME`을 명시적으로 호출한다. 편집한 파일은 덮어쓰지 않는다.

## 1. 호출: 표준 입력이 아니라 인자 두 개

상위 [진입점](../bench.sh)이 [빌더](../tools/submission-build.sh)를 통해 다음 호출을 소유한다. 사용자가 두 단계를 따로 실행하는 것이 아니다.

```sh
(cd "$SUBMISSION" && ./build.sh "$WORK" "$PREFIX" "$@")
```

- **현재 디렉터리**는 `TURTLE/implementations/`이다. 하위 소스 폴더의 이름, Make/CMake/Autotools/자체 스크립트 중 무엇을 쓸지는 레시피만 안다. 원본은 사전에 준비한다. TURTLE이 네트워크로 찾아오거나 폴더 이름으로 벤더를 추측하지 않는다.
- **`$1 = WORK`, `$2 = PREFIX`** 는 TURTLE이 만든 서로 다른 절대 경로다. 새 native build 시 둘 다 존재하며 비어 있다. 원본/제출 폴더에는 쓰지 않는다. in-tree 빌드만 가능한 프로젝트라면 원본을 `WORK`에 복사한 뒤 그 사본을 빌드한다. 설치 대상은 `PREFIX`이며 `/usr/local`이 아니다.
- **`$3 … = native argv`**. 루트 명령의 `--` 뒤 인자를 원소별로 그대로 받는다. `shift 2` 후 `"$@"`로 전달한다. 빈 인자·공백도 하나의 인자다. `eval`, 단어분리, 빌드 로그에서 플래그 추측을 하지 않는다. 옵션이 없으면 제출자가 정한 기본 구성이다. 사용자가 고른 암호·최적화 설정을 바꿔 빌드를 성공시키지 않는다. 지원하지 않는 옵션이나 사설 설치 경로/공유 빌드 조건과의 충돌은 거부한다.
- **출력 프로토콜은 stdout이 아니라 설치 트리와 종료 코드다.** 스크립트의 stdout/stderr는 로그다. `0`은 레시피가 설치를 마쳤다는 뜻일 뿐이다. 실패는 0이 아닌 값으로 반환한다. TURTLE은 원본 스크립트의 실패 코드를 보존하고 그 작업에서 링크나 실행을 시작하지 않는다. 신뢰하는 소스/레시피만 사용한다. 임의 스크립트를 격리하는 샌드박스가 아니다.

## 2. 소비용 SDK: 무엇이 있으면 충분한가

현재 소비 방식은 **로컬 Linux 네이티브 / ELF 공유 라이브러리 / pkg-config**다. 소스 프로젝트가 자체 빌드에 CMake를 써야 한다는 뜻은 아니다.

| `PREFIX` 하위 산출물 | 소비자가 확인하는 것 |
|---|---|
| 공개 헤더와 **동일 구성에서 생성된 헤더** | 브리지의 실제 컴파일 경로에 들어가야 한다. 예를 들어 빌드 중 정해진 알고리즘이나 구조체 레이아웃을 선언하는 구성 헤더를 빠뜨리지 않는다. 원본 소스 헤더만 복사하는 것으로 대체하지 않는다. |
| 실제 공유 라이브러리 및 필요한 개발용 링크 이름 | ELF DSO의 SONAME이 있어야 한다. 예컨대 `-lfoo`이면 사설 라이브러리 디렉터리에서 `libfoo.so`가 선택한 실제 파일로 해석되어야 한다. `lib/` 또는 `lib64/`라는 이름 자체는 계약이 아니다. |
| 사설 설치본을 지시하는 `.pc` | 파일은 `PREFIX` 아래에 두며 파일명(모듈 키)은 유일해야 한다. `pkg-config --cflags MODULE`과 `--libs MODULE`이 브리지와 두 역할을 컴파일·링크할 실제 사용 정보를 내야 한다. 폴더 이름·모듈 이름·링크 이름이 같을 필요는 없다. |

**이미 올바른 `.pc`가 있다면 그대로 설치하고 끝이다.** 새 전용 manifest, 헤더 목록, 파일별 해시, 라이브러리 순서 복사본을 요구하지 않는다. 원본이 CMake 타깃만 내거나 사용 정보를 전혀 내지 않으면 현재 backend는 그것만으로 링크할 수 없다. 그 경우에만 레시피가 원본 빌드의 결과로부터 빠진 소비 정보를 만들어 설치한다. 기존 여러 모듈의 조합만 빠졌으면 플래그를 복사하기보다는 `Requires:`로 묶을 수 있다([실제 예와 이유](examples/submissions/mbedtls/README.md)). 어느 대상이 연구자의 의도인지를 알 수 없다면 자동 추론하지 않는다.

<details>
<summary>현재 소비기가 받아들이는 구체 범위와 한계</summary>

- [링크 소비기](../tools/submission-link.cmake)는 사설 `.pc`를 탐색한다. 현재 모듈 이름은 영숫자 및 `.+_-` 범위다. 컴파일 옵션은 붙여 쓴 `-I경로`, `-D정의`, `-U정의`, `-pthread`를 처리한다. 적어도 한 사설 include 경로와 실제로 그 prefix에서 읽은 헤더의 의존 기록이 필요하다.
- 공개 링크 입력은 사설 `-L경로 -l이름` 또는 사설 공유 파일의 절대 경로, `-pthread`가 대상이다. 직접 명시한 라이브러리를 호스트 동명 파일로 바꿔서 통과시키지 않는다. DSO가 전이적으로 쓰는 운영체제 라이브러리까지 모두 사설 설치하라는 뜻은 아니다.
- 전략은 호환되는 모든 컴파일 플래그를 해석하는 범용 빌드 시스템이 아니다. 정적 전용·헤더 전용, 비 ELF, 교차 ABI·원격 보드, 지원하지 않는 공개 링크 옵션은 현재 범위 밖이다. 루트/프레임워크 빌드/작업 경로에 세미콜론, 콜론, 줄바꿈을 사용하지 않는다.
- 네이티브 Linux, C/C++ 컴파일러, CMake 3.20+, Make 또는 Ninja, nlohmann_json 3.12+, pkg-config, GNU tar/coreutils, flock, readelf 및 GNU 호환 링커/로더가 필요하다. 원본 빌드의 자체 도구는 별도다. JSON 패키지가 없다면 저장소의 `cmake -DNAME=json -DVERSION=3.12.0 -P tools/dependencies.cmake`로 준비할 수 있다. JSON은 개발자가 제출하는 빌드 명세가 아니다.

## 3. 선택·실패·재시도

| 상황 | TURTLE 동작 / 사용자가 볼 것 |
|---|---|
| 파일 누락·실행 권한 없음·한쪽이라도 기본 템플릿 | 종료 2. 해당 파일과 다음 동작을 표시하며 빌드·출력 생성 전 중단한다. 특정 벤더나 reference peer로 자동 전환하지 않는다. |
| 원본 빌드 실패 | `JOB/build/native.log`, `native.exit`. 레시피/원본/옵션을 고쳐 **새 작업 디렉터리**에서 재시도한다. |
| 여러 `.pc` | 실제 브리지 컴파일과 양쪽 링크로 후보를 검사한다. 이름이 다르더라도 소비 계획이 동등하면 한 번의 선택으로 처리한다. 유효 후보가 서로 다르거나 후보를 판정할 근거가 부족하면 멈춘다. 후보/실패 지점은 `JOB/build/link.*/candidates.tsv`와 같은 디렉터리의 로그에 있다. |
| 입력을 바꾸지 않고 모듈만 지정 | `./bench.sh --build-only --resume JOB --use MODULE` (원래 native 인자가 있으면 동일한 `-- …`도 전달). native build를 반복하지 않고 링크를 재검사한다. `--use`는 벤더 이름이 아니라 **사용자가 선택한 사설 pkg-config 모듈**이다. |
| 제출물·인자·기록된 환경·설치본 변경 / 이미 실행한 job | 기존 결과를 덮지 말고 `--out NEW_DIRECTORY`를 쓴다. 지문은 모든 호스트 도구와 모든 환경 변수의 재현성을 증명하지 않는다. 특히 구성에 영향을 주는 별도 환경을 바꿨다면 새 job으로 시작한다. |
| 링크 성공 | `JOB/build/bin/{client,server}`, `implementation.d`, 양쪽 `.map`, `module.txt`, `expected-libs.txt/.sha256`, `link-evidence.txt`. `--build-only`는 여기서 종료한다. 같은 구성에서 나중에 실행하려면 `./bench.sh --resume JOB`에 원하는 실행 옵션과 동일 native 인자를 준다. |

판정 기준은 **이번 호출의 종료 코드와 이번 링크 로그**다. 재개 후 새 선택이 실패했어도 기존 job에 직전 성공의 `bin/`이 남을 수 있다. `.d`는 컴파일러가 읽은 경로, 링크 맵은 링커가 사용한 입력, 로더의 `--list`는 사전 경로 확인이다. **빌드만으로 실제 핸드셰이크, 특정 PQ 그룹 협상, 최초에 제출한 모든 헤더의 출처, 또는 시간·사이클의 정확성을 확인한 것은 아니다.**

같은 계획으로 묶으려면 컴파일 인자, 정규화한 직접 링크 입력의 순서와 검색 경로, 역할별 로더 결과가 같아야 한다. `--as-needed`로 로드되지 않은 직접 입력도 맵에 나타나면 연구자의 선택이다. GNU 링커에서 누락 심볼만 확인된 후보는 호환되지 않는 것으로 구분한다. 다른 링크 실패는 불명으로 중단하고 해당 `.link.log`와 `.exit`를 남긴다. 현재 공통 사설 DSO 목록을 사용하므로, 두 역할이 서로 다른 사설 DSO 집합을 필요로 하면 합집합을 양쪽의 근거로 대신하지 않고 중단한다.

## 4. 편의성을 확인하는 합격선

새 이름의 호환되는 제출을 준비했을 때 A(원본)의 빌드 규칙 수정 **0**, B(TURTLE)의 벤더 등록·코어 수정 **0**, 완전한 사용 정보의 재입력·수동 산출물 복사 **0**, 준비 뒤 루트 명령 **1회**여야 한다. 두 시작 파일을 수정하거나 예시를 명시적으로 선택해 맞추는 비용은 숨기지 않는다. 독립적인 연구자 선택이 없으면 질문 0회, 선택이 필요하면 그 대상만 묻는다. [오프라인 검사](../tests/submission-build-contract.sh)는 미등록 이름의 라이브러리로 이 경계와 실패 동작을 확인한다. 이 대리 지표는 사람을 대상으로 한 사용성 실험이 아니다.


릴리스를 배포할 때에는 실제 Git 아카이브를 빈 곳에 푼 뒤 `sh tests/submission-distribution.sh "$export_dir"`로 시작 파일·실행 권한·개인 원본 제외를 검사한다. 이 검사는 사용자 작업 트리의 편집본을 템플릿과 같게 만들기 위한 것이 아니다.
