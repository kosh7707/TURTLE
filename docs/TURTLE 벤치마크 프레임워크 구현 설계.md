# TURTLE 벤치마크 프레임워크 구현 설계

TURTLE은 새 TLS 연결 하나에서 클라이언트 또는 서버 한쪽을 계측한다. 첫 구현 대상은 x86-64·ARM64 Linux에서 IPv4 TCP를 사용하는 OpenSSL 3.5.9와 wolfSSL 5.9.4다. **기본 실행에는 선택한 TLS 구현, 소켓, 단조 시계가 필요하다.** 레코드별 송수신, TCP 재전송, CPU 카운터는 해당 지표를 선택했을 때 관측한다. 아래는 구현할 동작이며, 현재 저장소와의 차이는 4절과 5절에 적었다. [S0–S4의 정의와 서버 인증·mTLS의 성공 조건](<for-paper/PQTLS 벤치마크 프레임워크 제안_ver1.md#scenarios>)

## 1. S3 한 건을 실행하는 순서

연구자는 실험 명세에 시나리오·인증 조건·응용 데이터·필수 지표와 선택 관측을 정하고, 배치 정보에 호스트별 실행 파일·주소·인증 자료 경로를 지정한다. 예를 들어 ARM64 보드의 OpenSSL 클라이언트에서 S3 첫 응답 지연을 잰다면, 상대는 mTLS 인증과 요청 `ping` 전체 검증 후 `pong`을 보내는 일반 wolfSSL 서버다. 서버를 계측하려면 역할별 지표를 선택해 새 연결을 연다. 일반 상대에는 계측 훅을 설치하지 않는다. 기존 서비스를 상대로 쓸 때에는 그 서비스에서 확인한 준비·인증·응답 근거를 남긴다. 양쪽의 성공 조건을 확인한 연결만 해당 과업의 비교에 포함한다.

~~~mermaid
flowchart LR
    C["제어기 (PC)"] -.->|준비·시작| E["측정 클라이언트 (보드)"]
    C -.->|준비·시작| P["일반 서버"]
    E <-->|TLS / TCP| P
    E -->|종료 후 사건 기록| A["분석기 (PC)"]
    C -->|설정·양쪽 결과| A
~~~

<a id="lifecycle"></a>

1. **사전 점검.** 제어기는 양쪽 빌드가 과업·인증·암호 구성을 지원하는지, 측정할 호스트가 필요한 관측점을 제공하는지 확인한다. 필수 지표를 얻을 수 없으면 이유를 돌려준다. 선택 관측만 사용할 수 없으면 그 이유를 남기고 실행한다. 명령은 `turtle check SPEC`을 신설하고, 기존 `turtle run SPEC OUTPUT`과 `turtle analyze RUN`의 호출 형식을 유지한다. [현재 CLI](../src/cli/main.cpp)
2. **준비.** 제어기는 시도 ID를 배정하고 네트워크·프로세스를 준비한다. 캡처를 요청했다면 첫 SYN 전에 수집기의 준비를 확인한다. 서버가 리슨하면 클라이언트가 접속한다. 두 역할이 TCP·TLS 객체 준비를 끝내면 시작 신호를 보낸다. 로컬에서는 파이프, 원격에서는 SSH로 시작한 프로세스의 입출력을 제어 통로로 쓴다. TLS 스트림에 계측용 헤더를 추가하지 않는다.
3. **측정.** 각 역할은 로컬에서 TLS를 진행한다. S3 클라이언트의 시작은 첫 핸드셰이크 호출 직전, 끝은 응답의 첫 평문 바이트를 돌려준 TLS 읽기의 반환 직후다. 두 시각 모두 클라이언트의 `CLOCK_MONOTONIC`에서 얻는다. 서버는 클라이언트 인증과 요청 검증을 마치면 곧바로 응답을 쓴다. 그 사이에 제어기와의 왕복을 넣지 않는다.
4. **확정과 회수.** 양쪽의 성공 조건을 확인하고 측정 구간을 닫은 뒤, TLS 객체가 살아 있을 때 협상·인증 근거를 조회한다. 종료 알림은 별도 구간으로 처리한다. 마지막 콜백이 끝나면 사건을 저장하고 소켓·수집기·이 시도가 만든 네트워크를 회수한다. 시간초과·피어 종료·회수 실패도 원래 ID에 남긴다. 재시도와 예열은 각자 새 ID를 쓰며 성능 표본과 구별한다.

<a id="adapters"></a>

독립 엔드포인트에서는 실행기가 소켓과 응용 버퍼를 소유하고 한 스레드가 연결을 진행한다. 새 TLS 구현을 붙일 때에는 준비, 핸드셰이크 진행, 평문 읽기·쓰기, 결과 조회, 해제를 공개 C 함수표에 연결한다. 기존 제품이 연결을 소유한다면 제품의 이벤트 루프가 TLS를 계속 진행하고, 관찰자는 접근 가능한 공개 경계에 붙인다. 일부 바이트를 성공적으로 썼을 때만 평문 위치를 옮긴다. 미완료 쓰기는 같은 작업 ID·버퍼·길이와 API가 요구하는 재시도 조건을 보존한다. S2·S4의 서버는 자기 Finished 이후 검증한 공개 경로에서, 필수 재시도 없이 선송신할 수 있는 첫 기회에 쓰기를 시도한다. S4의 큰 양방향 쓰기는 검증한 응용 크기·소켓 버퍼·I/O 경로 범위에서 지원한다. ## 2. 어느 지점에서 무엇을 재는가

블랙박스는 공개 TLS 호출과 응용 검증 사건으로 과업의 지연을 잰다. S3 클라이언트에서 OpenSSL의 호출 쌍은 `SSL_do_handshake`와 `SSL_read_ex`, wolfSSL의 호출 쌍은 `wolfSSL_connect`와 `wolfSSL_read`다. 시작 시각은 실제 진행 함수를 부르기 직전에, 읽기 시각은 반환 직후에 기록한다. 화이트박스는 같은 과업에서 선택한 관측을 더한다.

| 얻을 값 | 도구와 관측 지점 | 원자료와 단위 | 그 관측이 없을 때 |
|---|---|---|---|
| 핸드셰이크·첫 응답·전체 검증 지연 | 공통 실행기가 첫 TLS 진행 호출 직전과 성공 반환, 대상 평문을 돌려준 읽기 반환 직후, 내용 검증 직후에 `clock_gettime(CLOCK_MONOTONIC)`을 호출 | 역할·호출 ID, 평문 범위(B), 사건 시각(ns). 같은 역할의 끝에서 시작을 뺀다. | 필요한 끝점이 빠진 지표만 미확정 |
| TLS 레코드 헤더 통지 시각 | OpenSSL `SSL_CTX_set_msg_callback`의 `SSL3_RT_HEADER` 통지 진입 | 방향, 통지된 헤더 5 B, 로컬 시각(ns) | 동등한 공개 통지를 확인한 어댑터에서만 제공 |
| 공개 암호문 I/O의 요청·완료 | OpenSSL 기본 소켓 BIO의 `BIO_set_callback_ex` 사전·사후 통지. wolfSSL은 등록한 I/O 콜백의 진입·반환 | 호출 ID, 요청량·실제 처리량(B), 결과, 각 경계의 시각(ns) | 해당 공개 I/O 지표 미지원. 사용할 경로·경계 이름을 결과에 남김 |
| 레코드의 소켓 송신 직전·수신 직후 | OpenSSL의 추가 버퍼 없는 전달용 BIO 또는 wolfSSL의 `wolfSSL_CTX_SetIOSend`·`wolfSSL_CTX_SetIORecv`가 공통 소켓 함수를 호출. `send()` 직전에 시계를 읽고 반환값으로 실제 제출 범위를 확정. `recv()` 반환 직후 시계와 실제 수신량을 기록 | 호출 ID, 방향별 성공 바이트 범위 `[시작, 끝)`, 시각(ns), 스트림에서 조립한 외부 헤더. 첫 바이트를 제출한 `send` 진입과 마지막 바이트를 반환한 `recv`를 레코드에 대응 | 기본 BIO 통지만 있는 경로에서는 BIO 시각까지 제공. 시스템 호출 시각은 미관측 |
| 반복 전송량·반대 방향 레코드의 도달 | 측정 측 인터페이스 한 곳에서 libpcap으로 SYN 전부터 양방향 캡처. 분석기가 연결과 방향별 `ISN + 1`에 맞춰 SEQ·길이·ACK·SACK을 읽음 | PCAP 원본. 같은 방향에서 반복 관측된 범위(B), 관심 바이트를 실은 특정 사본의 누적 ACK가 상대 레코드 끝을 확인했는지 여부 | 캡처 부재·드롭·원점 누락 등으로 필요한 사본을 특정할 수 없으면 해당 판정은 미확정. 로컬 지연은 자체 사건으로 산출 |
| 호출 스레드의 CPU 시간 | 같은 스레드가 선택한 구간의 시작·끝에서 `CLOCK_THREAD_CPUTIME_ID`를 읽음 | 두 읽기의 차이(ns) | CPU 시간만 미관측 |
| 사용자 공간 사이클·명령어 | 대상 스레드에서 `perf_event_open`으로 커널·하이퍼바이저를 제외한 두 이벤트를 열고 구간 시작·끝에서 카운터 그룹을 읽음 | cycles, instructions, `time_enabled`·`time_running`(ns) | 권한 거부·이벤트 미지원·구간 내 `time_running` 증가분 0이면 카운터 지표를 산출할 수 없는 사유를 남김 |
| 함수별 CPU 표본 | 별도 시도에서 `perf record`로 측정 측 프로세스를 실행하고 종료 후 `perf script`로 해석 | `perf.data`, 실행 파일·모듈 빌드 ID, 함수별 표본 수 | 프로파일만 생략. 기본 시간 측정은 그대로 수행 |

OpenSSL의 소켓 BIO가 결과를 통지한 시점과 그 안의 소켓 호출이 반환한 시점은 별개다. 따라서 각 시도에 사용한 경로를 명시한다. 새 측정 항목이 기존 사건으로 계산되면 분석기만 확장한다. 새 시계 읽기처럼 실행 중 관측이 필요하면 해당 경계에 관찰자를 등록하고 시도 전에 활성화한다. 훅은 미리 할당한 버퍼에 기록하고 원래 반환값·오류 상태를 보존한다. [공개 TLS·BIO와 소켓 경계의 구분](<for-paper/PQTLS 벤치마크 프레임워크 제안_ver1.md#observation>)

레코드 시작이 `a`이고 외부 헤더의 본문 길이가 `L`이면 그 범위는 `[a, a+5+L)`이다. 헤더가 여러 호출에 나뉘면 5 B가 모일 때까지 이어 읽고, 여러 레코드가 한 `recv`에서 끝나면 같은 반환 사건을 참조한다. 방향별 누계는 로그 적재와 독립적으로 갱신한다. 예열에서 본 길이도 실제 연결의 헤더로 다시 확인한다. 실패·대기·0 B·`MSG_PEEK`는 누계에 더하지 않는다. 성공한 연결에서 각 방향의 `Finished` 뒤에 지정한 응용 데이터만 흐르고, 내부 패딩 0·고정 태그 길이·빈 응용 레코드 없음이 확인되면 뒤에서부터 응용 평문 총량을 채워 `Finished` 레코드 끝을 찾는다. 로컬 판정은 이 바이트 범위만 이용한다. TCP가 같은 바이트를 재전송할 때 소켓 훅은 다시 호출되지 않는다. TCP와의 대응은 사용자 공간과 캡처가 같은 암호문 스트림을 보는 경로에서만 수행한다. [Finished 판정과 지원 조건](<for-paper/PQTLS 벤치마크 프레임워크 제안_ver1.md#finished-boundary>) · [TCP 사본과 도달 판정](<for-paper/PQTLS 벤치마크 프레임워크 제안_ver1.md#tcp-seq>)

## 3. 누가 결과를 남기는가

| 작성 주체와 시점 | 산출물 | 보존할 근거 |
|---|---|---|
| 제어기, 준비부터 종료까지 | `manifest.json` | 시도 ID·목적, 과업과 계측 역할, 양쪽 바이너리와 설정, I/O 경로, 시계·네트워크·관측 지원 상태, 시드·실행 순서, 종료·누락 사유와 회수한 파일의 해시 |
| 측정 엔드포인트, 측정 구간 종료 후 | `events.jsonl`과 `client.result.json` 또는 `server.result.json` | 사건·호출 ID, 역할·방향·시계, 시각·단위·바이트 범위와 누락 구간. 역할 결과에는 인증·평문 검증 근거를 적는다. 반대편 결과 파일은 제어기가 일반 상대의 보고로 작성한다. |
| 선택 수집기, 별도 파일로 저장 | `capture.pcap` 또는 `perf.data` | 캡처 위치·링크 유형·오프로딩·드롭 수 또는 표본을 수집한 시도와 빌드 ID |
| 사후 분석기, 회수 후 | `analysis.json` | 지표값·단위·유효성, 근거 사건 ID나 패킷 사본, 분석 버전. 원자료에서 재계산할 수 있게 한다. |

각 파일은 시도 ID로 연결한다. 사건은 종료 후 기존 JSONL 기록기로 저장하고 PCAP과 CPU 표본은 원본 형식을 유지한다. 예를 들어 S4에서 `helo` 선송신과 `pong` 응답을 `he / lo / po / ng`로 읽었다면, 첫 응답 지연은 `po`를 돌려준 세 번째 TLS 읽기의 반환 시각에서 첫 핸드셰이크 호출 직전 시각을 뺀 값이다. 응답 전체 검증과 양쪽 인증 성공은 과업 성공의 별도 근거다. 실제로 협상한 그룹·암호 스위트·방향별 CertificateVerify 방식은 해당 연결에서 조회한다. 공개 조회가 어려운 서명 방식은 그 방향의 유효한 허용 방식이 하나이고 요구한 인증에 성공한 경우에 그 값으로 분류한다. 별도 검증 연결의 근거에는 그 연결 ID를 붙인다. ## 4. 빌드할 수 있는 기능과 보드에서 쓸 수 있는 기능

**빌드에서는 선택한 타깃에 필요한 헤더·라이브러리를 검사하고, 실행 전에는 그 기능을 쓸 호스트에서 장치·권한·실행 파일을 검사한다.** 제어기와 분석기는 연구자 PC에 둘 수 있다. 보드에는 선택한 TLS 엔드포인트와 런타임 의존성·인증 자료를 배치하고, 그 보드에서 수집할 때만 선택 수집기를 더한다.

| 의존성 | 빌드할 때 없으면 | 실행할 때 없거나 허용되지 않으면 |
|---|---|---|
| C++20 컴파일러, CMake 3.20 이상, JSON을 읽고 쓰는 타깃의 nlohmann/json 3.12 | 빠진 필수 도구·헤더를 명시하고 구성을 중단한다. 기본 생성기 Ninja가 없으면 설치된 Make로 `Unix Makefiles`를 명시할 수 있다. | 보드에는 빌드 도구를 설치할 필요가 없다. 선택한 바이너리의 런타임 의존성을 배포한다. |
| 선택한 OpenSSL 또는 wolfSSL 개발 파일 | `TURTLE_IMPLEMENTATION_DIRS`로 지정한 어댑터의 헤더·라이브러리가 없으면 해당 구성을 실패시킨다. 다른 TLS 구현은 독립적으로 빌드할 수 있다. | 라이브러리·공급자·필수 암호 구성 또는 인증 자료가 없으면 그 역할의 과업을 시작하지 않는다. |
| libpcap 1.10.6 헤더·라이브러리 | 제안 옵션 `TURTLE_WITH_PCAP=AUTO`에서 없으면 실시간 수집과 PCAP 읽기 타깃을 제외한다. 엔드포인트·기본 분석기는 독립적으로 빌드한다. | 캡처 장치·권한이 없으면 선택 TCP 관측을 생략한다. TCP 근거가 필수면 사전 점검에서 중단한다. 이미 보관한 PCAP은 수집 권한 없이 읽기 기능을 갖춘 PC에서 분석할 수 있다. |
| Linux PMU 헤더·시스템 호출 인터페이스 | 제안 옵션 `TURTLE_WITH_PMU=AUTO`에서 컴파일·링크할 수 없으면 카운터 수집을 제외한다. | PMU 이벤트와 권한은 대상 스레드에서 실제로 열어 확인한다. 외부 `perf` 명령이 없어도 이 카운터는 지원될 수 있다. |
| `ip`·`tc`(iproute2), `ethtool`, 네임스페이스·veth·netem | 실행 도구는 링크 의존성에서 제외한다. | 통제 망에서는 두 veth 쌍으로 클라이언트·라우터·서버를 잇고 라우터 양쪽 송신부에 `tc netem`을 적용한다. `tc -s`로 전후 큐 카운터를, `ethtool`로 오프로딩을 확인한다. 지정한 조건을 만들 수 없으면 해당 망 과업을 중단한다. 직접 연결·루프백은 별도로 선택할 수 있다. |
| `perf record/script`, `strace`, TShark, Python 보조 도구 | 기본 빌드에서 찾지 않는다. | 해당 프로파일이나 독립 검산을 수행할 때만 확인한다. 시스템 호출·패킷을 외부 추적하는 검산 시도와 일반 성능 시도를 구별한다. |

두 제안 옵션에서 `ON`은 필요한 구성 요소가 없으면 구성 오류, `OFF`는 탐색·링크 생략을 뜻한다. 교차 빌드에서는 호스트의 CMake·컴파일러를 쓰되 라이브러리·헤더·패키지는 대상 sysroot와 대상용 설치 경로에서만 찾는다. 대상 소켓·준비 대기·단조 시계를 컴파일·링크할 수 없으면 기본 엔드포인트 빌드를 중단한다. 장치와 권한은 실제 보드에서 확인한다. 기존 ARM64 툴체인의 패키지 탐색(`BOTH`)과 JSON·pcap을 함께 준비하는 의존성 묶음도 이 기준에 맞춰 분리해야 한다. [현재 툴체인](../tools/linux-arm64.cmake) · [의존성 묶음](../tools/dependencies.json)

현재 CMake는 최상위에서 libpcap을 필수로 찾고 CLI와 분석기에 캡처 타깃을 링크한다. 네이티브 구성 시험에서 nlohmann/json을 고정한 채 헤더·라이브러리 탐색 경로에 libpcap을 제공하면 성공했고, 빈 경로로 제한하면 `TURTLE_PCAP_INCLUDE_DIR`에서 실패했다. **목표 동작**은 libpcap 없는 ARM64 보드에서도 S3 첫 응답 지연을 재고 TCP 반복 바이트만 미관측으로 남기는 것이다. 반복 바이트 0은 해당 범위를 온전히 캡처해 실제로 반복이 없음을 확인한 경우에만 기록한다. ## 5. 구현 순서와 단계별 완료 조건

| 순서 | 바꿀 부분 | 완료를 판정할 실행 |
|---|---|---|
| 1. 한쪽 S3 | [실행기](../src/run/runner.cpp)와 [소켓 전송](../src/net/transport.cpp)에서 TU 프레이머를 제거한 경로를 연결하고, 제어기가 측정 엔드포인트와 일반 상대를 각각 선택하게 한다. 기본 타깃에서 pcap 의존성을 분리한다. | x86-64에서 대표 직접 발급 mTLS 구성 하나로 `ping/pong`을 끝낸다. 양쪽의 인증·내용 검증에 성공하고, 클라이언트 사건 두 개로 첫 응답 지연을 재계산한다. |
| 2. 과업과 어댑터 | OpenSSL·wolfSSL 공개 C 어댑터를 공통 실행기에 연결한다. SUPERCOP의 연산별 공통 검증·측정 방식을 따라 구현을 교체해도 같은 과업 시험을 쓴다. [SUPERCOP의 KEM 검증](https://github.com/jedisct1/supercop/blob/200cd30ca1f501463bd5cdd3da115a20d688d8fb/crypto_kem/try.c) | S0–S4 × 서버 인증·mTLS에서 지원하는 동종·교차 연결과 계측 역할을 바꿔 검증한다. S2·S4는 클라이언트 정지 시험과 양쪽이 진행하는 시험에서 같은 선송신 정책을 쓴다. 인증·내용 실패와 미완료 쓰기도 확인한다. |
| 3. 상세 계측과 영향 | 레코드·소켓 대응을 먼저 검증하고 그 위에 캡처와 CPU 관측을 붙인다. | 분할 헤더, 한 호출에서 끝난 여러 레코드, 가운데 로그 누락, 재전송을 독립 추적과 대조한다. 기록 끔·블랙박스·화이트박스는 같은 I/O 경로와 같은 최소 시작·종료 타이머로 비교한다. |
| 4. 실물 보드와 복구 | 제어기·분석기는 PC에 두고 대상용 엔드포인트를 배치한다. | libpcap·PMU를 제외한 ARM64 빌드에서 보드가 클라이언트와 서버를 각각 맡는다. 보드 기록을 PC로 옮겨 같은 지표값을 재계산한다. 필수 기능 부재·피어 종료·회수 중단 시 사유가 남고 재시도가 중복 집계되지 않는지도 확인한다. |

현재 ARM64에서 확인한 범위는 교차 컴파일과 링크까지다. 실물 보드에서의 역할 교체와 계측 비용은 위 실행을 마친 구성에서 보고한다.
