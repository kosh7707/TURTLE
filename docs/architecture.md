# 구조와 소유권

## 제어는 프레임워크에, TLS는 어댑터에 둡니다

Spring에서는 필요한 서비스를 명시적으로 전달하고 전체 실행 순서를 프레임워크가 관리하는 구조를 참고했습니다. Spring이나 전역 서비스 조회기는 사용하지 않습니다. SUPERCOP에서는 구현자가 공통 계약을 구현하고 같은 측정기를 사용하는 구조를 참고했습니다. SUPERCOP 코드를 복사하지 않았습니다.

```
명령행 / JSON 프로필
         │
         ▼
      config ─── model (값과 이름, 빌드 정보)
         │
         ▼
      lifecycle ─┬─ control (준비 신호, 대기, 자식 회수)
                 ├─ transport (TCP, 비차단 송수신)
                 ├─ capability (환경 점검, 코어 선택)
                 ├─ measure (시계, perf, 힙 추적)
                 ├─ record (고정 버퍼, 측정 후 파일 출력)
                 └─ 공개 함수표 → adapter → TLS 라이브러리

   *.jsonl / *.bin / *.keys.log
         ├─ turtle-interpret → 메시지와 레코드 범위
         └─ turtle-report    → 역할별 분포와 구간 합계
```

`transport`는 계측기나 기록기에 직접 의존하지 않습니다. 런타임이 비소유 관측 함수를 전달하여 두 부품을 연결합니다. `measure`는 기록 형식을 모르며, `record`는 TLS 메시지를 해석하지 않습니다. 분석기는 측정 실행 파일에 링크하지 않습니다. 각 부품은 CMake 라이브러리 대상으로 나뉩니다.

## 수명과 상태

지휘 프로세스는 표본마다 두 역할 프로세스를 만들고 결과를 기다립니다. TLS 모듈은 역할 프로세스에서만 `dlopen`합니다. 따라서 지휘 프로세스가 TLS의 전역 초기화나 할당기를 미리 건드리지 않습니다.

역할 프로세스의 계측기, 기록 버퍼, 어댑터 모듈과 컨텍스트는 명시적인 지역 객체입니다. 컨텍스트는 서비스보다 먼저, 연결은 컨텍스트보다 먼저 파괴합니다. 소켓은 프레임워크 소유이며 어댑터는 빌려 씁니다. C 할당 API가 사용자 인자를 받지 않을 때만 어댑터 안에 비소유 `thread_local` 연결 포인터를 사용합니다. 이는 서비스의 소유권이나 단일 인스턴스 조회 수단이 아닙니다.

컨텍스트 생성은 표본마다 새로 수행합니다. `--warmups N`은 같은 역할 프로세스와 컨텍스트에서 N개의 준비 연결을 먼저 실행한다는 뜻입니다. 그 뒤 `--connections M`개의 연결을 측정하며 M의 기본값은 1입니다. 준비 연결도 기록에 남지만 주 분포에서 제외하고, 측정 연결은 순서별로 분리해 서로 다른 표본의 같은 위치끼리 요약합니다. CPU 캐시가 완전히 차갑다거나 프로세스 바깥 상태까지 초기화됐다는 뜻은 아닙니다.

출력 파일과 소켓·epoll·버퍼는 제한 전에 마련합니다. 그 후 `RLIMIT_NOFILE`과 `RLIMIT_NPROC`를 0으로 낮춥니다. 이것은 측정 실행 조건이지 공격자를 막는 보안 격리 장치는 아닙니다. 지휘 통신은 별도 Unix 소켓으로 수행합니다.

## 측정 경로

라이브러리 호출 시작·완료, 송수신 진입·반환, 대기 시작·완료에서 스냅샷을 남깁니다. 실제 전송에 성공한 바이트만 방향별 스트림 위치를 증가시킵니다. 모든 TLS 메시지는 구현체가 만듭니다. 런타임은 특정 핸드셰이크 메시지 순서를 만들어 넣지 않습니다.

채널마다 관측자 하나를 선택적으로 연결하며, 함수형 계약은 `void (*)(void*, const Observation&) noexcept`입니다. 채널은 관측자 문맥을 소유하지 않으므로 그 문맥은 채널과 채널에서 빌린 `Io`보다 오래 살아야 합니다. 관측자는 사건과 성공한 바이트를 기록할 뿐 TLS 단계, 입출력 결과, 재시도나 제어 흐름을 결정하지 않으며, 전달된 페이로드·채널·프로토콜 상태를 바꾸지 않습니다. 이는 관측 유무가 TLS의 논리 결과를 바꾸지 않는다는 계약이지 실행 시간 비용이 없다는 뜻은 아닙니다. 관측과 복사 비용은 측정 경로에 포함될 수 있으며, 고정 기록 버퍼가 부족하면 측정 뒤 표본 유효성을 실패로 판정하되 이미 얻은 TLS 입출력 결과를 다른 값으로 대체하지 않습니다.

계측 읽기 → 고정 버퍼에 사건 추가 → 필요하면 성공한 스트림 복사를 수행합니다. 파일 출력, JSON 변환, 문자열을 돌려주는 협상 결과 조회는 주 구간 뒤에 둡니다. 다만 라이브러리 자체의 정상 할당은 실행의 일부이며 메모리 모드에서 관측합니다.

시계와 카운터는 순차적으로 읽으므로 하나의 원자적 시각이 아닙니다. 연산으로 분류한 토막에도 관측 콜백과 기록 복사 비용이 섞일 수 있습니다. 여기서 연산은 입출력·대기 밖의 호출 구간이라는 운영상의 분류이지 순수 암호 연산만의 비용이 아닙니다.

## 경계 검사와 테스트

`tests/`는 별도 CMake 프로젝트입니다. 부품 단독 시험 외에 실제 TCP를 쓰는 통합 시험이 있습니다. `scripts/check-modules.py`는 정적인 include 경계와 순환 의존을 검사합니다. 매크로로 만든 include나 CMake 링크 그래프 전체를 증명하는 도구는 아닙니다. 어댑터의 실제 컴파일 명령에도 내부 `src/` include 경로를 주지 않습니다.

새 기능은 먼저 한 책임의 부품에 넣습니다. 두 번째 구현이 없는 통로·계측 추상화나 범용 컨테이너, 서비스 조회 계층을 미리 만들지 않습니다. 공통 엔드포인트 제어 메시지 처리는 `endpoint_protocol.cpp`에, 실제 조회 캐시·wire·원자료와 모의 CA 실행은 `lookup_runtime.cpp`의 구체 `ClientLookupRuntime`과 CA 엔드포인트에 분리했습니다. `lifecycle.cpp`는 표본·프로세스·연결 순서를 조정하고 조회가 꺼진 정상 TLS 경로에서는 이 구체 런타임을 비활성 상태로 사용합니다. 새 범용 수명주기 추상화나 서비스 조회 계층을 추가한 분리는 아닙니다.
