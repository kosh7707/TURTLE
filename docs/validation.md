# 이전 컨트롤러 검증 결과 — 무엇을 실행했고, 무엇을 아직 모르는가

> 이 문서는 네이티브 실행 경계 도입 전의 역사적 결과다. 현재 릴리스의 실행 방법과 판정은 [네이티브 TLS 검증](native-validation.md)을 따른다. 아래 수치와 산출물 경로를 현재 릴리스의 결과로 해석하지 않는다.

범위는 **x86-64 Linux의 로컬 프로세스와 격리한 IPv4 TCP**다. 아래 시간·CPU는 이 환경에서 실제로 나온 예시이며 구현체 간 순위가 아니다. 실물 ARM64 보드는 연결하지 않았고 다른 하드웨어의 성능·권한·교차 재분석을 입증한 것으로 세지 않는다.

## 단측 mTLS S3: 예열 1회, 유효 표본 2개

설치 SDK를 사용하는 별도 빌드의 wolfSSL **클라이언트 하나**를 지정했다. TURTLE이 기본 OpenSSL 서버와 시험용 CA·서로 다른 말단 인증서를 준비했다. 각 시도에서 양쪽의 TLS 1.3 인증 성공, 서버의 요청 `ping` 4바이트 검증, 클라이언트의 응답 `pong` 4바이트 검증을 확인했다. 예열 `00000`은 통계에서 제외했다.

**G3(`48e7d3a`) 실행 ID:** `e412b8694ffb8a4db82f704acfa11663`. 이 버전과 같은 분석기를 사용해 아래 해시를 검산했다. 이후 도입한 `proc-exec.v1` 실행 이미지 증거나 `linux-netem.v1` 검사를 이 자료에 소급해 부여하지 않는다. 아래는 각 시도의 클라이언트 사건 1(첫 핸드셰이크 진입)부터 사건 5(첫 응답 평문 읽기 반환)까지다.

| 본 측정 | 같은 단조 시계의 경과 (ns) | cycles 원누계 차 | instructions 원누계 차 | PMU 활성 = 실제 실행 (ns) |
|---|---:|---:|---:|---:|
| 00001 | 2,665,100 | 8,010,690 | 24,880,860 | 1,921,800 |
| 00002 | 2,652,300 | 7,951,678 | 24,770,666 | 1,904,700 |

예를 들어 `00001`의 `client/counters.json`에서 양 끝 TID는 모두 784895다. wall은 83,566,229,494,749 − 83,566,226,829,649 ns, cycles는 17,951,784 − 9,941,094, instructions는 26,541,121 − 1,660,261이다. 이 구간의 PMU 활성 시간은 벽시계 경과가 아니다. 시간×주파수나 multiplex 보정값은 표에 넣지 않았다. 같은 분석기로 원자료를 다시 읽은 최상위 `analysis.json`의 SHA-256은 전후 모두 `b83ec497df1cd17d3c865e8340a0b14e7bf086420b40de97218cd5868e053777`이었다. 신규 실행의 정확한 시도 ID나 해시가 이 값과 일치할 필요는 없다.

해당 버전의 보관 결과는 다음 순서로 확인한다.

1. `manifest.json`의 `purpose`, 역할, 시도 ID, `directory`를 대조한다. 능력 시험과 예열은 측정 횟수가 아니다.
2. 각 시도의 `client/endpoint.json`, `server/endpoint.json`에서 협상·인증, 실제 평문 길이와 검증 결과를 확인한다. `client/events.jsonl`의 시작·끝 호출과 `client/counters.json`의 동일 경계·TID를 연결한다.
3. 최초 측정에서 반환 시각 − 진입 시각, PMU 끝 원누계 − 시작 원누계를 재계산한다. 양쪽의 과업이 정상이어도 필수 지표가 누락되면 유효 표본은 아니다.

## 검증 경계

| 시험 | 확인한 결과 |
|---|---|
| 배포 및 연동 | `48e7d3a` 릴리스 소스를 새 디렉터리에서 빌드한 OpenSSL·wolfSSL 회귀 40/40, 독립 채팅 앱 1/1. 함수표를 구현하지 않은 외부 CMake 역할 앱을 설치 SDK로 빌드했다. |
| PMU 실패 및 원자료 훼손 | `perf`가 PATH에 없어도 같은 스레드의 실측 이벤트를 읽었다. 접근 거부, 다른 TID, Δrunning=0, 다른 호출의 원누계 대입은 정상 측정값이 아니다. mTLS S3 결과를 복사해 본 측정 하나의 원자료만 바꾸면 그 시도가 탈락해 유효 표본 1개가 남았다. |
| 인증·응용 데이터 실패 | 클라이언트 인증서 누락, 인증 후 `pi`만 보내고 EOF인 두 경우 모두 서버 응답 0바이트, 유효 표본 0개. 신뢰된 CA가 서명해도 기대 DNS SAN이 틀리면 응답하지 않았다. |
| 양쪽 역할 및 시나리오 | 같은 wolfSSL 대상 실행 파일을 바꾸지 않고 기본 OpenSSL 상대와 S0–S4 × 서버 인증/mTLS × 클라이언트/서버 측정 = 20개 구성을 실행했다. 각 구성 예열 1회, 본 측정 1회, **20/20 유효**. S2/S4에만 별도 능력 시험을 수행했다. G4의 시나리오 회귀 **25/25**에는 20개 조합, 잘린 선송신 증거·CF 뒤 쓰기 거부, S4 최초 응답 900 ns와 전체 검증 1,150 ns를 구분하는 고정 벡터, 소켓 버퍼 1 KiB를 *요청*하고 양방향 안내·요청 각 16 KiB가 겹치는 S4 실연결이 포함된다. 이 숫자는 모든 TLS 라이브러리가 선송신을 지원한다는 뜻이 아니다. |
| 빌드 식별과 재분석 | `proc-exec.v1`은 READY와 종료 관측의 실제 실행 파일·로드된 실행 매핑을 식별한다. 선송신 시험의 대체 클라이언트는 대상 측정 표본이 아니다. 서버 측 빌드와 필요한 능력 증거가 본 측정과 대응해야 한다. 두 스냅샷 사이에만 존재한 모듈은 검증 범위 밖이다. |
| TCP 도달·손실 | 격리망에서 실제 패킷 캡처와 손실에 의한 반복 전송을 확인했다. 단측 mTLS S3에 각 방향 지연 8 ms(목표 추가 RTT 16 ms)를 적용했을 때 무손실, 클라이언트→서버만 20%, 서버→클라이언트만 20%에서 각각 본 측정 1개가 유효했다. 해당 본 측정의 중간 노드 qdisc 실측 드롭은 각각 0/0, 7/0, 0/12개(정방향/역방향). 권한 없는 환경에서 같은 망 설정을 명시하면 실행 실패·유효 표본 0개였다. |
| 별도 프로파일 | 기본 PMU 검증과 별개로 실제 OpenSSL TLS 연결에서 `perf` 함수 표본을 회수했다. 프로파일 시도는 일반 지연 표본에 합치지 않는다. |
| ARM64 | **사용자가 이번 인수를 보류하여 실기기 미검증.** 같은 Linux 빌드·원자료 회수 절차를 쓸 수 있도록 구성했지만, x86-64 성공이나 보관 파일 재분석이 실기기 인수를 대체하지 않는다. |

## 보관 자료 재생 — 현재 릴리스의 실측과 별개

[이전 검증 목록](evidence/validation.json), [mTLS S3 원자료](evidence/mtls-s3-loopback.tar.gz), [TCP 손실·선송신 PCAP](evidence/tcp-cases.tar.gz), [시나리오별 플라이트 자료](evidence/scenario-flights.tar.gz)는 **이관 전** 결과다. 예컨대 이전 자료의 S3 첫 본 측정 지연 2,409,900 ns는 위의 새 실행 수치가 아니다. 과거 판정에 현재의 단측 원누계 실측 자격을 소급해 부여하지 않는다. 일부 옛 외부 도구는 배포하지 않는다. [이관 내역](MIGRATION.md)에 보존·제거 범위를 기록했다.

루트 빌드 후 쓰기 가능한 새 디렉터리에 보관 자료를 풀어 재생한다. `analyze`는 원자료를 읽어 분석 결과 파일을 다시 쓰며 TLS 연결을 열지 않는다.

~~~sh
replay=$(mktemp -d)
tar -xzf docs/evidence/mtls-s3-loopback.tar.gz -C "$replay"
./build/turtle analyze "$replay"
~~~
