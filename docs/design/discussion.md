# 다음 설계 논의

2026-11-16의 [현재 설계](architecture.md)를 검토한 논의 안건입니다. 아래 권고는 아직 구현하거나 확정한 결정이 아닙니다. 현재 동작을 바꾸는 결정이 나면 공개 계약·실행 명세·자료 모델 중 무엇이 달라지는지 먼저 정하고 [결정 기록](../project/DECISIONS.md)에 이유를 남깁니다.

논의를 시작할 순서는 **비교 조건의 완전성 → 메시지 실행의 확장 범위 → 비용 해석 → 자료 계약 → 버퍼 전략**을 권고합니다. 현재 정상 TLS 실행을 유지하면서 무엇을 연구자가 통제할 수 있게 할지 정하는 순서입니다.

## 1. 자동 비교가 같은 조건이라고 판단하는 범위

현재 `report.py`는 구현체 이름·상대·역할·배치·연결 위치와 정해진 조건 필드를 대조합니다. 실제 실행 바이너리의 해시와 컴파일 조건, `io_chunk`, `max_message`, `event_capacity`는 자동 비교 키에 없습니다. 네트워크 조건 해시는 있지만 외부 관측 보고서의 누락 판정까지 읽어 비교 적격성을 결정하지 않습니다. 따라서 현재의 `exploratory`는 도구가 확인한 범위의 탐색 비교라는 뜻입니다.

먼저 정해야 할 것은 **비교마다 고정할 조건과 의도적으로 바꿀 조건을 어디에 선언할 것인가**입니다. 구현체 이름만 예외로 두는 현재 구조는 간단하지만 같은 이름으로 재빌드한 코드와 일부 계측 조건의 차이를 설명하기에 부족합니다.

| 선택 | 장점 | 부담·제약 |
|---|---|---|
| 현재 키와 수동 출처 대조 유지 | 실행·보고서가 작고 이해하기 쉬움 | 조건 누락을 매 실험에서 사람이 찾아야 함 |
| 연구 계획에 고정 조건·변경 축·출처를 명시 | 어떤 차이를 비교하는지 보고서에서 설명 가능 | 계획·manifest·보고서가 같은 조건 정의를 공유해야 함 |
| 모든 출처가 같은 실행만 비교 | 다른 빌드의 혼입을 쉽게 막음 | 구현체 변경 자체가 연구 축이므로 일괄 동일성 요구는 맞지 않음 |

두 번째 선택을 권고합니다. 양쪽 바이너리를 무조건 같게 요구하지 않고, 예를 들어 클라이언트 구현체만 변경 축으로 두면 서버의 **실제 바이너리 출처**를 고정합니다. 측정 경계를 바꾸는 설정도 조건에 포함합니다. CPU affinity·주파수·커널·네트워크·외부 관측 중 필수 조건은 연구 계획에서 명시하고, 수집하지 않은 값은 일치한다고 가정하지 않습니다.

완료 기준은 정상 실행 두 쌍에서 의도한 축만 바꾸면 비교가 만들어지고, 선언하지 않은 버퍼·I/O·상대 바이너리 조건이 달라지면 차이와 제외 이유가 설명되는 것입니다. 현재 수집 자료에 없는 사실을 사후 추정해 채우지는 않습니다.

## 2. 메시지 함수 교체와 프로토콜 순서 변경의 경계

현재 ClientHello 함수 교체는 실제 TLS를 완료합니다. 그러나 메시지 순서, 상호 인증 분기, 키 전환 전 평문 flush 지점은 `Execution`에 있습니다. 새로운 메시지, 인증 흐름 또는 키 전환을 연구하려면 코어를 수정해야 합니다. `support()`의 문자열은 설명 정보이며 기계적인 지원 협상표가 아닙니다.

여기서 정할 질문은 **지원하는 정상 TLS 1.3 순서 안의 함수 교체에 집중할지, 연구자가 메시지 순서도 제공하게 할지**입니다. 전자를 유지하면 native 경계와 계측 의미를 작게 관리할 수 있습니다. 후자는 실험 범위를 넓히지만 구현체가 상태 진행을 다시 소유하지 않도록 해야 합니다.

권고는 먼저 필요한 새 정상 경로 하나를 구체적인 연구 사례로 정하고, 그 사례에 필요한 단계·보호 경계·완료 조건을 선언하는 작은 계획 표현을 검토하는 것입니다. 임의 콜백이 소켓·시계나 다음 메시지 진행을 소유하는 확장은 현재 원칙과 충돌합니다. 실제 필요 없이 범용 상태 머신 언어나 플러그인 ABI를 만드는 것은 권고하지 않습니다.

추가로 `turtle_result`는 KEM·캐시 전용 필드를 이미 포함합니다. 새 기법을 붙일 때마다 코어 직렬화를 바꿀지, 공통 성공 증거와 기법별 관측을 나눌지도 같은 논의에서 결정해야 합니다. 현재는 임의 기법의 결과를 함수표 하나만으로 확장할 수 있다고 설명하면 안 됩니다.

완료 기준은 기존 네 시나리오의 메시지·레코드·배치와 비용 경계가 유지되고, 선택한 새 정상 경로에서도 프레임워크가 모든 단계와 실제 I/O를 통제하는 것입니다.

## 3. 공통 단계 비용을 어디까지 같은 작업으로 볼 것인가

조립·처리·전환이라는 공통 이름은 실행 경계를 맞추지만 native 내부 작업의 분배를 같게 만들지는 않습니다. 어떤 구현체는 `BEGIN`에서 버퍼를 만들고, 다른 구현체는 연결 생성 때 준비합니다. 수신 전환에는 메시지 복사와 transcript 갱신이 포함될 수 있습니다. `framework_remaining`에는 결과 확인과 계측의 일부 비용도 들어갑니다.

정할 질문은 **메시지별 수치를 실행 경계의 비용으로 제시할지, 라이브러리 내부 작업 종류까지 공통 기준으로 재분류할지**입니다. 후자는 더 세밀하지만 패치와 계측이 native 실행을 더 바꾸고 공유 작업을 억지로 배분할 위험이 있습니다.

우선은 전체 프로토콜·준비·첫 사용 비용과 현재 직접 단계 비용을 유지하고, native 작업이 어느 경계에 들어가는지 구현체별 대응표를 출처와 함께 강화하는 것을 권고합니다. 추가 계측이 필요하면 특정 질문에 필요한 구간만 도입합니다. 상세 계측 실행의 시간 차이나 표본 비중을 일반 실행의 정확한 함수 시간으로 환산하지 않습니다.

검증은 단계 합의 비중첩과 잔여값, 다른 계측 깊이의 조건 구분, 준비·재사용의 비용 귀속을 확인해야 합니다. 관측 부담을 연구하려면 별도의 통제된 정상 실행으로 수집하고, 현재 자료에서 임의로 빼지 않습니다.

## 4. 사건 필드와 실패 자료를 더 명시적으로 만들 것인가

현재 `stream_offset`은 조립·처리에서는 메시지 내부 위치이고 레코드·I/O에서는 스트림 위치입니다. `type`도 사건 종류에 따라 다른 이름 공간을 씁니다. 문서로 해석할 수 있지만 분석기를 구현할 때 문맥을 빠뜨리기 쉽습니다. 가용 상태도 manifest의 수단별 상태와 값의 null에 나뉘어 있습니다.

정할 질문은 **현행 작은 사건 구조를 유지할지, 범위 종류·관측 위치·연결 관계를 자료 형식에서 직접 드러낼지**입니다. 권고는 실행 중에는 고정 크기 사건 배열을 유지하고, 저장 시 `message_offset`, `stream_offset`, 관계·관측 상태를 구별하는 표현을 검토하는 것입니다. 필드 의미를 바꿀 때는 새 계약을 명시하고 구형 형식을 추측해서 읽지 않습니다.

실패 자료의 경계도 함께 정해야 합니다. 현재 정상적인 예외는 이미 기록한 사건을 남길 수 있지만 관측자 이전 실패·강제 종료·실패 중인 스트림의 완전한 저장은 보장하지 않습니다. 정상 경로의 재현에 필요한 진단 수준을 먼저 정하고, 이를 공격·내구성 시험 프로젝트로 넓히지 않습니다.

완료 기준은 큰 정수와 가용 상태, 공유 비용의 한 번 기록, 양쪽 메시지·레코드 대응이 유지되고, 범위 종류를 잘못 읽을 여지가 줄어드는 것입니다. 사후 저장을 늘려도 측정 중 파일 출력은 도입하지 않습니다.

## 5. 큰 메시지의 조각 인터페이스와 실제 스트리밍

현재는 전체 메시지를 조립·재조립한 다음 단계로 갑니다. 4096바이트 조각 호출은 진행 계약을 검증하지만 native 파서가 수신과 겹쳐 실행되는 구조는 아닙니다. 출력 배치·캡처·사건 배열도 유한하며 설정 조합에 따라 메시지 용량보다 먼저 부족해질 수 있습니다.

선택지는 전체 메시지 모델을 유지하면서 필요한 용량을 사전에 계산하는 방법과, 생성·보호·제출 및 수신·처리를 부분적으로 겹치는 실제 스트리밍 실행기를 만드는 방법입니다. 후자는 메모리를 줄일 수 있지만 transcript 접근, 서명·검증 시점, 묶음 정책, 실패 시 남는 출력과 비용 경계를 모두 다시 정의해야 합니다.

당장 권고하는 방향은 첫 번째입니다. 연구할 메시지 크기와 레코드 정책을 기준으로 예약 용량을 명시하고 불가능한 조합을 측정 전에 설명합니다. 진짜 스트리밍이 필요한 연구 질문이 생기면 현재 모델과 다른 실행 조건으로 분리해 검토합니다. 조각 API가 있다는 이유만으로 현재 구현을 스트리밍이라고 부르지 않습니다.

## 논의 이후 문서를 갱신하는 기준

결정할 때는 바꾸는 연구 질문, 유지할 불변 조건, 소스 계약·실행 명세·자료 계약 중 바뀌는 범위, 정상 실행에서 확인할 증거를 함께 남깁니다. 구현하지 않은 제안은 이 문서에 두고 현재 설계 문서에는 옮기지 않습니다. 실행 당시 자료의 명세·경로·해시는 수정하지 않고, 보존 위치가 바뀌면 작업 공간의 이동 원장으로 설명합니다.
