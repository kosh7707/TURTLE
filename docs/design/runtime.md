# 엔드포인트 실행과 통신

## 소유권과 실행 순서

`src/main.cpp`는 빌드할 때 정한 역할의 설정을 읽고 `lifecycle::run_endpoint`를 호출합니다. `turtle-client`와 `turtle-server`는 독립 프로그램입니다. 상대 프로세스의 부모 PID, 파일 경로, CPU 번호나 공유 파일시스템을 요구하지 않습니다. 서버는 데이터·제어 수신 주소를, 클라이언트는 데이터·제어 접속 주소와 자기 출발 주소를 받습니다. 현재 주소 계약은 숫자 IPv4입니다.

각 프로그램은 자신의 기록기·고정 버퍼·계측기·어댑터 연결·서비스·TLS 컨텍스트를 구성합니다. 연결은 컨텍스트보다 먼저, 컨텍스트는 서비스와 모듈보다 먼저 파괴합니다. `Meter`와 모든 TLS 호출은 같은 엔드포인트 스레드에서 실행합니다. `builtin`은 실행 파일에 연결한 함수표를 전달하고, `module`은 명시한 파일의 `turtle_adapter_v3`를 엽니다. 두 경로의 공개 ABI는 3입니다.

`module`의 `dlopen`만 `MODULE_BEGIN/END`로 기록합니다. `builtin`의 해당 구간은 `not_applicable`이며 프로그램 진입 전 로딩은 관측하지 않습니다. `SETUP_BEGIN/END`는 두 방식 모두 어댑터의 `setup()` 호출 경계입니다.

별도 TCP 제어 연결의 프로토콜 2는 준비 JSON에 역할, 실행 ID, 컨텍스트 ID, 표본·묶음 번호와 공유 시나리오를 담습니다. 길이는 네트워크 바이트 순서의 4바이트이며 최대 16KiB입니다. 준비가 끝나면 277바이트 고정 제어 프레임으로 준비·시작·연결 완료·기록 완료 또는 중단을 교환합니다. 파일 경로·CPU 번호·절대 단조 시각은 보내지 않습니다. 수동 실행의 클라이언트가 만든 실행 ID를 서버가 채택하며 외부 실행기는 양쪽에 같은 ID를 지정할 수 있습니다.

계측 지원, 컨텍스트, 버퍼와 출력 준비를 마친 뒤 시행마다 준비 신호를 교환하고 새 TLS TCP 연결을 만듭니다. TLS 객체를 연 뒤에는 완료 경계까지 제어 메시지를 처리하지 않습니다. 비차단 TLS 대기는 데이터 소켓만 감시합니다. 제어 바이트는 TLS 스트림·해독·전송량에서 제외됩니다. 기본은 프로세스당 컨텍스트 하나, 준비 연결 0개, 측정 연결 1개입니다. `--warmups N --connections K`를 명시하면 같은 컨텍스트로 연결을 재사용하며 첫 측정 연결도 남깁니다. 같은 컨텍스트의 여러 연결을 독립 표본으로 합치지 않습니다.

`scripts/run-local.py`는 `turtle-local`로 빌드 폴더에 복사되는 외부 실험 실행기입니다. 요청한 표본마다 독립 프로그램을 새로 시작하고 시도 원장·로컬 CPU 배치·선택적 관측 경계만 소유합니다. `scripts/run-study.py`는 이 실행기에 명시한 반복 설정을 전달합니다. 기본 외부 표본 수 역시 1입니다. 네트워크 관측을 위한 선택적 로컬 소켓은 준비·정리 경계에서만 사용하고, 관측 없는 로컬 실행과 수동 실행에는 만들지 않습니다.

TLS 엔드포인트의 `RLIMIT_NPROC=0`은 유지하되 새 TCP와 대기 객체를 만들 수 있도록 `RLIMIT_NOFILE`은 유지합니다. 자원 제한은 보안 격리 장치가 아닙니다. 표본 수·연결 수·버퍼와 단일 기한은 명시한 조건이며 실패를 피하려고 자동 축소하지 않습니다.

### CPU 위상과 배치 한계

환경 기록은 커널 판, `perf_event_paranoid`, 허용·물리 CPU 목록과 CPU별 package/core ID, `thread_siblings` 목록을 담습니다. `perf_event_paranoid`를 읽지 못하면 값은 `null`이고 이유를 따로 남깁니다. 형제 목록의 `null`은 sysfs 목록을 읽지 못함, 빈 목록은 읽었지만 형제가 없음을 뜻합니다. 각 형제의 `online`도 알 수 없으면 `null`입니다. 형제가 현재 affinity 허용 범위 밖에 있어도 물리 자원 공유 정보이므로 목록에서 제외하지 않습니다.

독립 엔드포인트는 자기 장비에서 허용된 CPU 하나만 선택합니다. 상대 장비의 CPU 위상을 검사하지 않습니다. 로컬 실행기는 자기 소유의 실행기·클라이언트·서버·필요한 조회 서비스를 서로 다른 것으로 확인한 물리 코어에 배치합니다. 그 로컬 배치를 확인할 수 없으면 실행을 중단합니다. 선택한 CPU의 온라인 또는 상태 미상 형제가 있으면 그 형제의 유휴 상태는 확인하지 못했고 코어 전용 사용도 보장하지 못했음을 경고합니다. `--no-affinity`는 역할 배치 자체가 확인되지 않은 조건입니다. WSL과 같은 가상화 환경의 위상은 게스트에 보인 정보일 뿐 호스트 물리 코어 전용을 증명하지 않습니다. 설정 단계의 위상 확인과 CPU 고정도 실행 전체의 독점 사용을 보장하지 않습니다.

환경 식별값은 이런 위상·형제 온라인 상태·`perf_event_paranoid` 같은 안정 사실을 포함합니다. 경고 문구, 읽기 실패 이유, 순간 부하와 관측 시각은 그룹을 불필요하게 나누지 않도록 환경 식별값에 넣지 않습니다.

### 성능 카운터 범위와 상태

`measurement.perf_scope`는 `user` 또는 `user+kernel`이고 기본값은 `user`입니다. 둘 다 `pid=0`, `cpu=-1`, `inherit=0`, `exclude_hv=1`로 해당 역할 스레드만 셩니다. `user`는 `exclude_kernel=1`, `user+kernel`은 `exclude_kernel=0`입니다. `user+kernel`이라도 다른 스레드·전체 시스템·하이퍼바이저 비용을 포함하지 않습니다. `CLOCK_THREAD_CPUTIME_ID`로 읽는 스레드 CPU 시간은 이 성능 카운터 범위 선택과 별개입니다.

원자료는 요청 `perf_requested_scope`, 상태 `perf_status`, 실제 `perf_effective_scope`를 따로 남깁니다. `available`일 때만 실제 범위가 요청과 같은 문자열이며, `disabled`·`unsupported`의 실제 범위는 `null`입니다. 두 `null`은 알려진 비활성·미지원 상태이며 필드 누락의 알 수 없음과 다릅니다. 미지원은 `cycles_open`, `instructions_open`, `reset`, `enable`, `initial_read` 중 실패 단계와 errno, 설명을 따로 남깁니다.

- `perf=false`, `user`: 요청 범위는 남기고 `disabled`, 실제 범위 `null`로 정상 실행합니다.
- `perf=false`, `user+kernel`: 서로 모순되는 설정이므로 실행 자료를 만들기 전에 거절합니다.
- `perf=true`, `user`: 카운터를 열지 못하면 `unsupported`, 실제 범위 `null`로 남기고 시간 측정과 정상 TLS를 계속합니다.
- `perf=true`, `user+kernel`: 요청을 적용하지 못하면 측정 정보를 원자료에 복사한 뒤 엔드포인트를 이유 있는 실패로 끝내고 시도 원장에도 남깁니다. `user`로 낮추어 다시 시도하지 않습니다.

두 카운터·그룹 초기화·초기 읽기까지 성공해야 `available`입니다. 실행 중 읽기는 여전히 사건별 `null`이 될 수 있고, `enabled=running=0`은 실제 계수 성공의 근거가 아닙니다. `perf_complete`는 필요 카운터가 모두 있고 `running>0`이며 `running<enabled`가 아닌 사건에서만 유지됩니다. 프로그램은 호스트의 `perf_event_paranoid`나 capability를 바꾸지 않고 실제 그룹 설정 결과를 사용합니다.

현재 WSL 환경에서 `user+kernel` 하드웨어 카운터 성공을 확인했다고 주장하지 않습니다. 설정 속성과 각 실패 단계, 파일 설명자 정리, 엄격한 요청 거절은 결정적 시스템 호출 대역 시험으로 확인합니다. 호스트의 실제 계수가 가능할 때만 실제 카운터 값을 근거로 삼습니다.

조회 기능은 별도 `turtle-lookup` 프로그램을 사용합니다. 클라이언트가 자기 객체 저장본을 읽고 조회 서비스의 데이터·제어 주소로 연결합니다. 조회 서비스는 자기 객체 파일과 CPU만 소유하며 TLS `Role`에 포함되지 않습니다. 로컬 실행기는 조회가 켜졌을 때만 서비스를 배치합니다. 조회를 끄면 객체 파일·서비스·가짜 결과를 만들지 않습니다.

클라이언트는 연결마다 캐시를 같은 `empty` 또는 `fixed-snapshot` 저장본으로 복원하고, 응답을 검증해 `USABLE_OBJECT`가 된 뒤 TLS를 시작합니다. 이 객체는 수정하지 않은 TLS 인증서 입력을 대체하지 않습니다.

클라이언트의 TLS `Meter`, 조회 힙 추적기, 모의 CA의 `Meter`와 힙 추적기는 소유권을 나눕니다. 조회 사건의 시계·성능 카운터는 클라이언트 TLS `Meter`를 한 번 읽고 힙 필드만 조회 도메인 값으로 바꿉니다. 조회용 성능 카운터 그룹을 따로 열지 않습니다. 모의 CA 프로세스·입출력·대기·힙은 CA 프로세스의 원자료에 독립적으로 남깁니다.

TCP 준비에서는 `ESTABLISHED`와 설정 후 조회한 비차단 플래그·`TCP_NODELAY`·송수신 버퍼·수신 시각 옵션도 확인합니다. 실제 버퍼 크기를 요청값과 혼동하지 않고 각 연결의 원자료에 남깁니다. TLS 실행 시험은 새 소켓이 가능한 제한값과 시행별 생성 순서를 확인합니다. 준비 동기화 뒤에는 상대의 ClientHello가 먼저 도착할 수 있어 읽지 않은 바이트 0을 요구하지 않습니다.

`--context` 입력은 각 엔드포인트가 자기 역할의 파일만 읽어 셋업에 전달합니다. 외부 반복에서 같은 입력 경로를 지정할 수 있지만 앞 표본의 출력으로 자동 갱신하지 않습니다. 실제 입력 크기와 지문을 남깁니다.

## 연결과 시험 준비 확인

`PeerSession`은 데이터 수신 소켓과 제어 수신·접속 소켓을 소유합니다. 역할 실행기가 반환하고 TLS 컨텍스트·어댑터가 정리된 뒤 이 소켓을 닫습니다. 서버에는 `--listen IP:Port`, `--control-listen IP:Port`를, 클라이언트에는 `--connect IP:Port`, `--control-connect IP:Port`를 지정합니다. 주소·포트 개별 옵션도 같은 필드를 설정합니다.

제어 연결의 준비 순서는 TCP 접속 → 실행·시나리오 합의 → 자기 컨텍스트·버퍼·요청 기능 준비 → 양쪽 준비 상태 교환 → 시작입니다. 프로토콜 2의 초기 JSON에서 TLS 엔드포인트는 `readiness_version=1`을 요구하고, 별도 조회 서비스는 0을 사용합니다. 버전이 다른 엔드포인트를 준비된 것으로 취급하지 않습니다. 기존 `TCP_READY` 경계에서 양쪽 성공을 확인한 뒤 길이 제한이 있는 준비 요약 JSON을 같은 제어 스트림에서 교환합니다. 자기 준비 중 실패하면 `FAILED` 메시지로 상대에게 이유를 알립니다.

`preparation.stage`는 `local_environment`, `listen`, `control_accept` 또는 `control_connect`, `scenario`, `local_preparation`, `peer_preparation`, `ready` 중 마지막 도달 단계입니다. 제어 연결의 실제 주소, 시나리오 일치, 자기·상대 준비 여부와 계측 지원을 남깁니다. 상대 요약은 준비 단계의 선언이며 파일 경로·CPU 번호·절대 시각은 보내지 않습니다. 준비 중에는 TLS 데이터 접속과 인증서 인증을 각각 `not_probed`, `not_checked`로 남기고 실제 시행에서 확인합니다. 첫 측정 연결을 소비하는 사전 TLS 확인은 하지 않습니다. 정상 시행에 실패해도 준비 완료 기록은 당시 상태로 보존하며 `valid`·`failure_phase`·`invalid_reason`이 최종 결과를 나타냅니다.

외부 로컬 실행기용 `--ready-file`은 포트와 `state=listening`, `test_ready=false`를 알립니다. 수신 소켓 생성 알림이며 시험 준비 완료 알림이 아닙니다. 준비 상태의 JSON 구성·교환은 TLS 측정 구간 밖에서 수행하고 최종 원자료는 정리 단계에서 씁니다. 단계별 재시도는 처음 정한 기한을 연장하지 않습니다.

## 로컬 TCP와 물리 네트워크

TLS 데이터와 엔드포인트 간 제어는 `AF_INET/SOCK_STREAM` TCP 소켓입니다. `127.0.0.1`로 연결하면 커널의 TCP/IP와 루프백 장치를 사용하며 물리 NIC를 지나지 않습니다. `0.0.0.0`은 서버가 모든 로컬 IPv4 주소에서 수신하도록 하는 바인드 주소입니다. 클라이언트는 루프백이나 서버의 실제 IP를 사용합니다. 같은 호스트의 LAN 주소도 로컬 경로로 처리될 수 있으므로 주소만으로 NIC 통과를 단정하지 않습니다. `ip route get ADDRESS`와 인터페이스 관측으로 실제 경로를 구별합니다. [Linux IPv4 소켓 설명](https://man7.org/linux/man-pages/man7/ip.7.html).

로컬 netem 실험의 veth는 네트워크 네임스페이스 사이에 패킷을 전달하는 가상 Ethernet 장치입니다. TCP·큐·지연·손실·재전송을 실제로 수행하지만 물리 NIC·케이블 비용의 검증은 아닙니다. 물리 경로는 별도 장비 또는 명시적으로 구성한 외부 경로에서 확인해야 합니다. [Linux veth 설명](https://man7.org/linux/man-pages/man4/veth.4.html).

넓은 뜻의 IPC에는 프로세스 사이의 TCP도 포함됩니다. 여기서 구별할 것은 전송 경로입니다. 독립 실행의 엔드포인트끼리는 TCP를 사용합니다. `turtle-local`과 선택적 관측기에는 로컬 경계 확인용 Unix 소켓이 남아 있으며 TLS 바이트를 운반하지 않습니다. 두 실행 파일을 터미널에서 직접 시작하면 그 보조 소켓도 필요하지 않습니다.

OpenSSL `s_time`은 지정한 `host:port`에 TLS 연결을 반복해 연결 수·시간·선택적 전송량을 집계하는 성능 클라이언트입니다. 서버는 별도로 실행하며 로컬 접속도 TCP입니다. `-new`는 새 세션 연결을 선택하고 `-www`를 생략하면 응용 데이터를 보내지 않습니다. `-new`와 `-reuse`를 모두 생략하면 두 방식을 순서대로 시도합니다. 강건성 시험 도구나 양쪽 역할의 세부 비용 계측기는 아닙니다. TURTLE은 연결 경로를 참고하되 전체 핸드셰이크·첫 연결 보존·양쪽 개별 계측 계약을 유지합니다. [공식 명령 설명](https://docs.openssl.org/3.5/man1/openssl-s_time/), [관찰한 OpenSSL 3.5.4 소스](https://github.com/openssl/openssl/blob/openssl-3.5.4/apps/s_time.c).

## 비차단 호출과 관측

`transport::Channel`은 빌린 소켓·출력 버퍼와 비소유 관측 콜백을 가집니다. 계측기나 기록 부품에는 의존하지 않습니다. 실제 송수신 전후에 호출하는 관측 콜백은 런타임이 소유하며, 성공한 바이트만 방향별 스트림과 누적 위치에 넣습니다. 수신은 `recvmsg`로 수행하고, 사용 가능한 소프트웨어 커널 시각은 원래 실시간 시계 값으로 따로 기록합니다. 이 값이 모든 바이트의 개별 도착 시각이라는 뜻은 아닙니다. 선택적 커널 송신 시각은 [TCP 분석](../analysis/tcp-analysis.md)의 `SO_TIMESTAMPING` 경로로 수집합니다. 하드웨어 시각은 미지원입니다.

### I/O 반환 캡처의 측정 경계

송수신 반환에서는 먼저 연결·호출·순번·결과·스트림 범위를 채우고 고정 버퍼의 반환 사건 공간을 예약합니다. 성공 바이트가 있으면 그 뒤 방향별 스트림에 복사하고, 첫 성공 수신이면 `first_receive`를 반환 사건 순번으로 고정합니다. 커널 원시 시각이 있으면 같은 연결·스트림 범위와 새 순번을 가진 `KernelRx` 공간도 예약합니다. 이 준비를 모두 끝낸 뒤 `snapshot()`을 한 번만 읽고 같은 값을 반환 사건과 `KernelRx`에 저장합니다. 따라서 시스템 호출뿐 아니라 이 시점 전의 프레임워크 캡처 작업도 I/O 구간에 듭니다.

다만 서버 기본 주 구간은 첫 성공 수신 반환의 스냅샷에서 시작합니다. 따라서 그 첫 수신의 고정 공간 준비와 바이트 복사는 서버 주 구간 시작보다 앞이며, 해당 구간의 `io_ns`에 들지 않습니다. 이는 서버의 기존 첫 수신 경계를 유지한 결과입니다. 후속 I/O 반환의 캡처 작업은 각 I/O 구간에 포함됩니다.

I/O 진입 사건은 기존 경계를 유지합니다. 연결·호출·순번 식별을 먼저 채운 뒤, 사건 종류·스트림 위치·요청량을 채우고 기록 공간에 넣기 전에 스냅샷을 읽습니다.

`Meter::read()`는 하나의 시계 호출이 아닙니다. 사용 가능하면 성능 카운터 그룹을 읽고, 그 뒤 스레드 CPU 시계, 단조 시계, 힙 상태 순으로 읽습니다. 단조 시각은 힙 읽기보다 먼저이며 각 계측값의 내부 관측 시점도 완전히 같지 않습니다. 힙 계측을 지원하지 않아도 복합 읽기 뒤에 힙 선택값만 비웁니다.

스냅샷 뒤에는 반환 사건 공간 대입, 선택적 `KernelRx` 공간 대입, 관측자와 채널의 복귀 비용이 남습니다. 고정 저장 공간이므로 이 대입은 새로 할당하지 않지만, 스냅샷 뒤의 비용은 후속 연산 구간에 들 수 있습니다. 그러므로 `computation`이나 레코드 귀속 구간을 순수한 TLS 라이브러리 시간이라고 부르지 않습니다. `calibration`은 복합 읽기의 진단 분포를 보존할 뿐 각 구간에서 빼지 않으며, 보정으로 참값을 복원했다고 주장하지 않습니다.

`src/lifecycle/capture.hpp`의 `Capture<Meter>` 템플릿은 고정 기록 버퍼가 `read()` 시점에 어떤 상태인지 시험하기 위한 컴파일 시점 연결면만 제공합니다. 실제 경로는 `measure::Meter`를 직접 사용하며 런타임 가상 호출·함수 포인터 시계·일반 계측 프레임워크를 추가하지 않습니다. 관측 함수는 기존처럼 `noexcept`이고 반환값이 없습니다.

`WantRead`나 `WantWrite`를 반환한 호출은 같은 작업과 같은 버퍼로 다시 실행합니다. 성공한 부분 바이트만 응용 버퍼의 위치를 이동합니다. 응용 데이터가 있는 시나리오에서는 각 방향의 고정 패턴을 검증합니다. 요청·응답과 서버 Ping의 진행 순서는 [공통 실행·계측 계약](prototype.md)을 따릅니다. 실제 TLS 어댑터에서는 TLS 1.3, 전체 핸드셰이크, 인증서 검증 성공을 확인합니다. `mock`은 암호화도 인증서 검증도 하지 않으며 선언과 미완료 설명에 그 차이를 남깁니다.

개정 4의 클라이언트 구간은 첫 핸드셰이크 호출부터 마지막 성공 TLS API 반환까지이며 서버는 첫 성공 TLS 수신 반환부터 같은 역할의 마지막 성공 TLS API 반환까지입니다. 호출 완료 사건의 `result`는 `Step` 값이며, 응용 호출에는 `AppResult.step`을 기록합니다. `Complete`는 2이며 서버 응용 준비 `ApplicationWriteReady`는 4입니다. 라이브러리 직접 소켓 비교에서는 프레임워크 송수신이 보이지 않으므로 `library-only`로 표시하고 바이트와 커널 관측이 없음을 남깁니다.

### 시나리오의 종료 (개정 4)

시나리오의 종료는 엔드포인트가 마지막 메시지나 응용 데이터를 TLS에서 처리하여 자기 역할을 마친 시점입니다. 송신은 마지막 TLS 송신 API가 성공 반환할 때까지입니다. 수신은 마지막 데이터를 검증·복호화하고 응용 버퍼에 전달한 TLS 수신 API가 성공 반환할 때까지입니다. TCP 패킷 도착·소켓 제출·상대의 수신·소켓 정리와 구별합니다. 여기서 응용 버퍼 전달은 TURTLE이 넘긴 버퍼에 복호화 결과를 쓰고 반환한 상태이며 별도 응용 스레드의 소비를 뜻하지 않습니다.

| 시나리오 | 클라이언트 종료 `CALL_END` | 서버 종료 `CALL_END` |
|---|---|---|
| `handshake` | ClientFinished 송신을 포함한 `handshake_step(Complete)` 반환 | ClientFinished 검증을 포함한 `handshake_step(Complete)` 반환 |
| `server-ping` | Ping 수신·처리 뒤 전체 Pong의 마지막 성공 `app_send` 반환 | Ping 송신 뒤 전체 Pong의 마지막 성공 `app_recv` 반환 |
| `finished-ping` | Finished+Ping 수신·처리 뒤 전체 Pong의 마지막 성공 `app_send` 반환 | Finished+Ping 송신 뒤 전체 Pong의 마지막 성공 `app_recv` 반환 |
| `client-request` | 요청 송신 뒤 전체 응답의 마지막 성공 `app_recv` 반환 | 요청 수신·처리 뒤 전체 응답의 마지막 성공 `app_send` 반환 |

부분 성공을 첫 완료로 오인하지 않습니다. 요청한 전체 길이를 누적한 마지막 호출을 선택하며 `WantRead`·`WantWrite` 재시도는 종료가 아닙니다. 서버의 조기 Ping 준비 반환도 핸드셰이크 완료가 아닙니다. `role_runtime.cpp`는 해당 `CALL_END` 순번을 보관하고 `connections[].end_sequence`에 씁니다. 성공한 뒤에 새 종료 스냅샷을 읽지 않습니다.

인증서·Finished·레코드의 TLS 검증은 해당 라이브러리 호출 안에 있습니다. 프레임워크의 `peer_verification`은 그 결과를 조회하고, 시험 페이로드 비교는 복호화된 내용이 고정 패턴인지 확인합니다. 순수 핸드셰이크의 결과 조회, 마지막 수신 뒤의 패턴 비교, `APPLICATION_*_END` 표식과 제어 동기화는 종료점 밖입니다. 단, 수신 뒤 송신이 이어지는 역할의 패턴 비교와 응용 교환 전 인증 결과 조회는 시작과 최종 송신 사이에 있으므로 경과 시간과 `gap` 또는 호출 연산에 포함됩니다. 이를 순수 TLS 연산으로 표시하지 않습니다.

최종 검증에서 실패하면 이미 종료 사건이 있더라도 실행은 무효입니다. 종료 시각의 관측과 정상 실행의 판정은 별개입니다. 기록을 쓴 뒤 정리·완료 확인에 실패한 경우도 실패 표식과 외부 원장에 따라 보고서에서 제외합니다.

`CALL_END`는 어댑터 반환 직후의 복합 계측 읽기입니다. 라이브러리의 마지막 기계 명령과 동일한 물리 시각이라는 뜻은 아닙니다. I/O 반환 캡처와 마찬가지로 기록·계측 자체의 비용이 남습니다. 보정값을 빼지 않습니다.

소켓 정리는 주 구간에 포함하지 않습니다. 기존 `CLOSE_BEGIN/END`에는 선택적 송신 시각 진단 수집과 TLS 객체 해제가 들어가며, 그 뒤의 운영체제 `close()` 비용을 따로 측정하지 않습니다. 이 표식을 순수 소켓 정리 벤치마크라고 부르지 않습니다. 조회 서비스의 `SCENARIO_END`도 최종 패턴 확인 뒤 남기는 별도 서비스 사건이므로 TLS의 마지막 API 반환과 같은 시각으로 취급하지 않습니다.

개정 3은 순수 핸드셰이크의 인증 결과 조회 완료 또는 응용 완료 표식까지를 기록했습니다. 원자료 형식 3·어댑터 ABI 3·제어 프로토콜 2는 유지하고 종료 의미만 측정 계약 개정 4로 구별합니다. 판독기는 개정 3의 `end_sequence`를 그대로 재사용하며 새 경계로 옮기지 않습니다. 개정 3·4는 자기 역할과 상대 역할의 비교 조건에서 각각 분리합니다.

| `handshake_call_begin_to_application_complete` (`client-request`) | 클라이언트: 첫 `handshake` `CALL_BEGIN`→전체 `app_recv` 완료; 서버: 첫 `handshake` `CALL_BEGIN`→전체 `app_send` 완료 | 응용 교환 전에 완료한 해당 역할의 인증 처리를 포함합니다. 서버는 첫 수신 전 대기도 포함할 수 있습니다. | 경계 사이에 처리한 값을 포함하되 따로 분리하지 않습니다. | 클라이언트는 퐁 수신, 서버는 퐁 송신 완료까지 포함 | `handshake_call_begin_to_application_complete_elapsed_ns`, `handshake_call_begin_to_application_complete_thread_cpu_ns` |
| `client_hello_to_finished_send` | 클라이언트: ClientHello 레코드 성공 송신 반환→클라이언트 Finished 레코드의 마지막 바이트 성공 송신 반환 | 서버 인증서 검증과, 상호 인증이면 클라이언트 인증 메시지 생성·송신을 포함합니다. 서버의 클라이언트 Finished 검증 완료를 뜻하지 않습니다. | 경계 사이의 ChangeCipherSpec은 포함합니다. 클라이언트 Finished 뒤의 티켓은 제외합니다. | 제외 | `client_hello_to_finished_send_elapsed_ns`, `client_hello_to_finished_send_thread_cpu_ns`, `client_hello_to_finished_send_cycles` |
| `server_client_hello_to_finished_send` | 서버: ClientHello 레코드의 첫 바이트를 포함한 성공 수신 반환→서버 Finished 레코드의 마지막 바이트 성공 송신 반환 | 서버 인증 메시지 묶음 생성을 포함하지만 클라이언트 Finished 검증과 상호 인증의 클라이언트 인증서 수신·검증은 제외합니다. | 경계 사이에 보낸 ChangeCipherSpec은 포함하지만 후속 티켓은 제외합니다. | 제외 | `server_client_hello_to_finished_send_elapsed_ns`, `server_client_hello_to_finished_send_thread_cpu_ns`, `server_client_hello_to_finished_send_cycles` |

여기서 “포함”은 경계 사이의 경과 시간에 든다는 뜻입니다. 각 작업의 순수 CPU 비용을 분리했다는 뜻이 아닙니다. `record_computation_attribution`은 기본 주 구간의 연산 구간에 레코드 근거를 붙이는 연결별 보기이며 추가 그룹 지표나 자동 비교를 만들지 않습니다.

### 콜백과 라이브러리 직접 소켓 경로의 관측 가능성

OpenSSL 어댑터는 `framework_io=true`인 콜백 경로와 `false`인 라이브러리 직접 소켓 경로를 지원합니다. wolfSSL과 Mbed TLS는 라이브러리 직접 소켓 경로를 지원하지 않으며 해당 설정을 거절합니다. 지원 여부를 추정하거나 가짜 결과를 만들지 않습니다.

콜백 경로에서는 `transport::Channel`을 지난 TLS 스트림 바이트와 I/O 사건을 기록합니다. 수신 시각 설정이 실제로 준비됐으면 커널 수신 사건을 수집할 통로도 사용할 수 있습니다. 그러나 `availability.kernel_receive_events.available=true`는 **수집 경로가 설정·지원됐다는 뜻**이지 특정 실행에서 커널 시각 사건이 하나 이상 생겼다는 증거가 아닙니다. `raw_timestamp_ns`가 있는 원자료 사건을 확인해야 발생을 주장할 수 있습니다.

라이브러리 직접 소켓 경로에서는 TLS 라이브러리가 소켓을 직접 사용하므로 프레임워크의 TLS 스트림, I/O 사건과 커널 수신 사건을 볼 수 없습니다. 세 항목을 0으로 쓰지 않고 `available=false`, `reason=native_socket_io_not_observed`로 기록합니다. 클라이언트는 첫 핸드셰이크 호출부터 위 시나리오 표의 마지막 성공 TLS API 반환까지의 경계가 남으므로 경과 시간과 스레드 CPU 차이는 보고할 수 있습니다. 다만 `computation`·I/O·대기·틈 분해와 스트림 바이트 지표는 `null`입니다. 서버는 주 구간 시작인 첫 성공 프레임워크 수신을 볼 수 없으므로 `start_sequence=null`, `primary_window.available=false`, 이유 `server_first_receive_not_observed`로 남기며 경과·CPU를 만들지 않습니다.

TLS 인증과 32바이트 핑퐁이 성공한 기능 유효성과 특정 지표의 관측 가능성은 별도 상태입니다. 라이브러리 직접 소켓을 쓰는 서버의 주 구간이 없어도 기능 결과는 유효할 수 있고, 반대로 지표가 존재해도 응용 검증이나 시도·네트워크 무결성 실패를 성공으로 바꾸지 않습니다.

### 채널 관측자 켬/끔

프로필 JSON의 `measurement.channel_observer`는 기본 `true`입니다. CLI 옵션이나 공개 adapter ABI를 추가하지 않고 내부 실행 설정에만 둡니다. 필드가 없는 이전 프로필·원자료는 켬으로 읽습니다.

`false`는 `transport::Channel`에 전달하는 관측 함수 포인터만 `nullptr`로 바꿉니다. 같은 콜백 `Io.send/recv`와 `send/recvmsg`, 비차단 재시도, 버퍼 크기, 소켓 설정과 커널 시각 설정 재조회를 유지합니다. `Capture::invoke`의 TLS 호출 시작·끝, 대기 사건, 키 로그·평문 알림, 성능 카운터와 교정도 계속 동작합니다. 따라서 관측자 끔 상태를 **무계측** 실행이라고 부르지 않습니다. 관측자 켬/끔 차이는 전체 계측 비용의 수학적 상한이나 하한이 아니며 서버의 계측 없는 외부 기준선을 대신하지 않습니다.

끔 상태에서는 프레임워크 스트림 복사와 I/O·KERNEL_RX 사건만 수집하지 않습니다. 표본은 `observation_level=observer-disabled`이고 `tls_stream`, `io_events`, `kernel_receive_events`가 모두 `available=false`, `reason=channel_observer_disabled`입니다. 빈 스트림 파일을 관측된 0바이트로 해석하지 않습니다. 서버의 기존 첫 수신 기반 주 구간도 계속 사용할 수 없습니다.

호출 사건은 양쪽 모드에 남으므로 보고서는 양 역할에 `handshake_call_begin_to_application_complete` 공통 경계를 계산합니다. 시작은 측정 연결의 첫 핸드셰이크 `CALL_BEGIN`, 끝은 각 시나리오의 마지막 응용 동작을 완성한 성공 `CALL_END`입니다. 기본 요청·응답은 클라이언트 수신/서버 송신이며 서버 Ping은 클라이언트 송신/서버 수신입니다. 순수 핸드셰이크에는 이 응용 구간이 해당하지 않습니다. 부분 전송과 재시도는 요청한 응용 바이트가 모두 끝날 때까지 합산합니다. 이 공통 경계는 라이브러리 직접 소켓이나 관측자 끔 경로에서 사용할 수 없는 서버 주 구간을 대체하거나 만들어 내지 않는 별도 진단 경계입니다.

셋업 시작과 끝의 스냅샷은 실제 호출 경계에서 얻고, 어댑터의 할당 함수 지원 선언을 확인한 후 기록합니다. 지원되지 않는 힙 관측은 0이 아니라 빈 값입니다. 누락되거나 다중화된 성능 카운터는 `perf_complete=false`입니다.

## 저장과 무효 표본

선택한 컨텍스트 입력 폴더의 `client.context.bin` 또는 `server.context.bin`을 셋업 전에 읽습니다. 셋업에 전달한 바이트 수와 저장한 바이트 수, 직렬화 지원 선언을 기록합니다. 역할별 컨텍스트 출력은 미리 열린 파일에 씁니다. 저장된 상태의 의미는 어댑터 선언에 따르며, 세션 재개를 허용한다는 뜻이 아닙니다.

엔드포인트는 정상 시나리오를 완료하지 못하면 `valid=false`, `failure_phase`, `invalid_reason`을 남기고 종료합니다. 이미 원자료를 쓴 뒤 완료 확인에 실패하면 `<역할>.failure.json`에 같은 실행 ID와 이유를 기록하고 실패로 종료합니다. 보고서도 이 표식을 반영합니다. 기존 원자료는 덮어쓰지 않으며 실패 표본을 성공 표본으로 대체하지 않습니다.

### 엔드포인트 기한과 외부 시도 원장

공유 시나리오에 `timeout_ms`와 `flush_grace_ms`를 넣고 각 엔드포인트가 자기 단조 시계에서 기한을 한 번 정합니다. 시행·부분 입출력·재시도마다 기한을 새로 주지 않습니다. 원격 절대 시각을 받아 로컬 기한으로 쓰지 않습니다. TLS 종료 뒤 기록 완료에는 로컬 정리 유예를 사용합니다.

외부 실행기는 자기 시계로 프로세스 실행을 제한하고 `attempts.jsonl`에 요청·시작·최종 상태를 동기 기록합니다. 정상 종료 외의 상태는 `timeout`, `error`, `incomplete`로 남깁니다. `fail-fast`는 실패 뒤 남은 시도를 `not_attempted`로 두며 `fixed-attempts`도 원래 요청한 수를 늘리지 않습니다. 기본 표본은 1개입니다. `requested = started + not_attempted`, `started = success + timeout + error + incomplete`를 유지합니다. 회수 시 먼저 기록 유예를 기다리고 종료 요청 뒤 250ms 안에 끝나지 않은 소유 프로세스를 강제 종료·회수합니다. 수동 실행에는 외부 원장이 필요 없으며 명시한 양쪽 원자료로 보고할 수 있습니다.

### 로컬 네트워크 배치

`scripts/netem-study.py`가 클라이언트·라우터·서버 네임스페이스와 veth 두 쌍을 소유합니다. 조회를 켜면 조회 서비스 네임스페이스와 링크를 더합니다. 네트워크와 관측기를 준비한 뒤 `turtle-local`이 각 네임스페이스에서 독립 실행 파일을 시작합니다. 네임스페이스 FD·프로세스 회수·관측기는 엔드포인트 설정이 아닌 외부 실험 책임입니다.

고정된 로컬 TLS 데이터 포트는 44330, 제어 포트는 44331입니다. 조회 데이터·제어는 44332·44333입니다. netem은 데이터 포트와 방향을 선택하는 필터 아래에만 붙이고 제어는 지연·손실 대상에서 제외합니다. 패킷 파일은 제어를 별도 흐름으로 보존하며 TLS 집계에는 넣지 않습니다. 지정 손실·커널 재전송 수집도 TLS 데이터 흐름을 선택합니다. 호스트 네트워크 불변·여섯 단계 관측·소유 자원 정리를 출처 기록에 남깁니다.

서로 다른 장비에 수동 배치할 수 있지만 SSH 배포·실행·회수 자동화와 교차 장비 시계 교정은 이번 범위 밖입니다. 로컬 이름공간 검증을 두 물리 장비나 ARM 검증으로 표현하지 않습니다.

## 검증과 빌드 연결

제품 빌드와 `tests/`의 시험 빌드는 별도 CMake 프로젝트입니다. 아래 부품 시험과 실제 TLS 통합 시험으로 실행·관측 계약을 확인합니다.

- `control_frames_and_deadlines`와 전송 부품 시험은 부분 제어 프레임·대기·실제 TCP 입출력 경계를 확인합니다.
- `independent_endpoint_actual_tls`는 세 라이브러리의 네 시나리오를 별도 작업·출력 폴더에서 실행합니다. 자기 CPU만 지정하고 서로 다른 시계 영역을 기록하며, 양쪽 해독과 명시한 파일 쌍의 분석을 확인합니다.
- `prototype_scenarios_actual_tls`와 `pipeline_*`은 라이브러리 간 연결, 두 송신 정책·인증 조건, 부분 응용 입출력과 상세 사건을 확인합니다.
- `pure_tls_netem_actual`, `network_rate_cwnd_actual_tls`, `io_path_external_metadata`는 로컬 실행기의 독립 프로그램 배치, 실제 네트워크 조건·제어/데이터 구분·자원 정리를 확인합니다.
- `lookup_*`, `bithac_actual_cached_certificates`, `mlkem_actual_dispatch_tls`는 조회·캐시 비용과 실제 기법 호출을 검증합니다. 모의 어댑터 성공을 실제 TLS 성공으로 세지 않습니다.

현재 빌드·시험·정적 검사와 원자료 대조 결과는 [검증 문서](../project/validation.md)에 모읍니다.

## 측정 뒤 조회와 고정 실패

문자열을 돌려주는 협상 결과 조회는 해당 시나리오의 마지막 TLS API 성공 반환 뒤에 실행합니다. 순수 핸드셰이크도 같은 원칙을 따릅니다. 따라서 버전·암호 방식·그룹·서명 이름을 만드는 할당이 주 측정 구간에 들어가지 않습니다. 실제로 관측된 암호 방식·그룹·서명은 요청 프로필과 비교하며, 빈 값은 요청값으로 채우지 않고 관측하지 못했다는 설명을 남깁니다. 호출 완료 사건에는 응용 바이트의 요청량과 실제 처리량도 기록합니다. 어댑터가 실패하면 제공된 오류 설명을 무효 이유에 보존합니다.

CPU 고정을 요청했으면 실패를 경고만 남기고 진행하지 않습니다. 엔드포인트의 고정 실패는 자기 원자료를 무효로 만들고, 로컬 실행기의 배치 실패는 외부 실행 오류로 남깁니다. `pinned_cpu`는 실제 성공한 CPU 번호이며 고정하지 않았거나 실패했으면 -1입니다.
