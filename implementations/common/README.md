# 실제 TLS 어댑터의 지원 범위

각 모듈은 공개 계약만 포함하며 컨텍스트와 연결을 직접 소유합니다. 소켓은 빌려 쓰고 닫지 않습니다. 정상 경로의 TLS 1.3 전체 핸드셰이크만 비교합니다. 컨텍스트 저장은 세 어댑터 모두 빈 바이트열을 돌려주며, 비어 있지 않은 저장 상태 입력은 지원하지 않습니다.

## 고정 의존성과 빌드

`TURTLE_DEPS_ROOT=<캐시 폴더> scripts/build-deps.sh`는 다음 판을 내려받아 직접 빌드합니다. OpenSSL과 Mbed TLS의 배포 압축 파일은 SHA-256을 검사하고 wolfSSL은 태그의 커밋을 확인합니다. CMake에 같은 `TURTLE_DEPS_ROOT`를 전달합니다. 시험 실행 자체는 네트워크에 접속하지 않습니다.

- OpenSSL 3.5.4: TLS 1.3과 공식 키 로그·메시지·할당 콜백을 제공합니다. 공유 라이브러리, `no-tests`로 빌드합니다. 시스템 OpenSSL 3.0 이상도 빌드할 수 있지만 결과의 실제 버전을 기록하며 고정 판과 혼동하지 않습니다.
- wolfSSL 5.8.2-stable: TLS 1.3, 타원곡선, 사용자 입출력, 비밀값 콜백을 사용합니다. 정적 위치 독립 코드로 빌드합니다. `SHOW_SECRETS`는 비밀값 콜백을 노출하기 위한 빌드 조건이며 파일 키 로그 기능은 끕니다. 비밀값은 호스트의 메모리 저장 함수로만 전달합니다. 난수 씨앗은 `WOLFSSL_GETRANDOM` 설정으로 리눅스의 `getrandom` 시스템 호출에서 얻습니다. 따라서 연결을 열 때 `/dev/urandom` 파일을 새로 열 필요가 없습니다.
- Mbed TLS 3.6.4: 기본 TLS 1.3 설정과 키 내보내기 콜백을 사용합니다. 정적 위치 독립 코드로 빌드하며 예제·라이브러리 자체 시험은 별도로 실행하지 않습니다. 호스트 할당 함수를 설치할 수 있도록 `MBEDTLS_PLATFORM_MEMORY`를 명시해서 빌드합니다.

빌드 스크립트는 각 빌드를 마친 뒤 `<TURTLE_DEPS_ROOT>/manifests/`에 판, 원본 확인값, 빌드 설정을 텍스트로 남깁니다. 이 파일을 보면 해당 의존성 폴더가 어떤 설정으로 만들어졌는지 다시 확인할 수 있습니다.

세 어댑터의 공통 프로필은 AES-128-GCM/SHA-256, P-256 키 교환과 ECDSA P-256 인증서, 호환용 ChangeCipherSpec 사용, 티켓 0장입니다. 서버 인증과 상호 인증을 지원합니다. 암호군은 모든 어댑터에서 `TLS_AES_128_GCM_SHA256` 하나로 고정하며 다른 값이나 후보 목록은 거절합니다. wolfSSL과 Mbed TLS 어댑터는 공통 프로필보다 넓은 설정을 지원한다고 주장하지 않습니다. OpenSSL은 암호군 외 그룹·서명 설정을 라이브러리에 전달합니다. 레코드 크기 제한과 인증서 압축은 아직 세 어댑터 모두 지원하지 않습니다.

## 키 생성과 인증서 처리 경계

셋업에서는 세 어댑터 모두 신뢰 CA와 해당 역할의 로컬 인증서 체인·개인 키를 읽습니다. 이는 핸드셰이크에서 받은 상대 인증서의 해석·검증과 다른 작업입니다. 서버 인증 프로필의 클라이언트와 상호 인증 프로필의 양쪽 역할은 상대 인증서를 핸드셰이크 안에서 해석하고 검증합니다. 서버 인증 프로필의 서버는 상대 인증서를 받지 않습니다. 라이브러리 내부의 모든 ASN.1 작업이나 자격 증명 캐시가 같은 위치에 있다고 주장하지 않습니다.

- OpenSSL 3.5.4는 클라이언트의 ClientHello와 서버의 ServerHello 키 공유를 만드는 핸드셰이크 경로에서 P-256 임시 키를 생성합니다. 로컬 자격 증명은 셋업에서 읽고, 상대 인증서 DER 해석과 검증은 핸드셰이크 안에서 수행합니다.
- wolfSSL 5.8.2-stable은 셋업에서 지원 곡선과 선호 그룹 목록을 P-256 하나로 고정합니다. 연결을 여는 `open()`에서는 키를 만들지 않습니다. 클라이언트는 ClientHello 구성 중에, 서버는 ClientHello 처리 중에 라이브러리의 기본 지연 생성 경로로 P-256 임시 키를 만듭니다. 로컬 자격 증명은 셋업에서 읽고, 상대 인증서는 핸드셰이크의 `ProcessPeerCerts` 경로에서 처리합니다.
- Mbed TLS 3.6.4는 클라이언트와 서버의 TLS 1.3 키 공유 구성 경로에서 P-256 임시 키를 생성합니다. 로컬 자격 증명은 셋업에서 읽고, 상대 인증서 DER 해석과 검증은 핸드셰이크 안에서 수행합니다.

`open()`은 주 핸드셰이크 기준 구간보다 앞에 있습니다. 따라서 wolfSSL에서 연결을 열 때 `wolfSSL_UseKeyShare`를 호출하면 양 역할의 임시 키 생성이 기준 구간에서 빠지고, 다른 두 구현과 비교하는 대상이 달라집니다. 첫 `handshake_step()` 앞에 같은 호출을 옮기는 방법도 서버에서는 첫 수신보다 먼저 끝나므로 해결이 아닙니다. 그룹 목록만 셋업에서 고정하고 기본 지연 생성을 사용하는 이유는 추가 연결 상태나 역할별 분기 없이 클라이언트 생성은 ClientHello 구성에, 서버 생성은 ClientHello 수신 뒤 처리에 두기 위해서입니다.

위 위치 설명은 고정한 OpenSSL 커밋 `c1eeb9406b6142148f267594197d853403d10208`, wolfSSL 커밋 `decea12e223869c8f8f3ab5a53dc90b69f436eb2`, Mbed TLS 커밋 `c765c831e5c2a0971410692f92f7a81d6ec65ec2`의 소스 경로를 기준으로 합니다. wolfSSL의 `wolfSSL_CTX_set_groups`는 그룹 목록을 설정할 뿐 키를 생성하지 않고, ClientHello 구성과 처리 경로가 목록에서 선택한 공유를 지연 생성합니다. 이 근거만으로 실제 통신의 공유 개수나 HelloRetryRequest 부재를 검증했다고 보지는 않습니다. 실제 바이트에서 ClientHello 공유 하나와 ServerHello의 P-256 선택, 일반 ServerHello 하나, 재개 및 HelloRetryRequest 부재를 별도로 확인해야 합니다. 다른 판, 다른 그룹, 재개, HelloRetryRequest, 인증서 형식별 내부 비용은 확인 범위 밖입니다.

## 계측과 관측 한계

- 세 어댑터 모두 비차단 호스트 입출력을 사용합니다. OpenSSL만 명시적으로 선택한 기본 소켓 경로도 지원합니다.
- 세 어댑터 모두 NSS 형식 TLS 1.3 키 로그를 호스트에 전달합니다. 원자료에는 비밀값이 있으므로 실험용 인증서와 로컬 통신에만 사용해야 합니다.
- OpenSSL은 평문 메시지 알림을 지원합니다. 나머지 어댑터는 지원하지 않습니다.
- OpenSSL 메모리 모드는 `CRYPTO_set_mem_functions`를 초기화 전에 설치합니다. 이 외부 C API에는 사용자 인자가 없으므로 어댑터 내부의 비소유 `thread_local` 연결 포인터만 사용합니다. 한 역할 프로세스에 메모리 모드 컨텍스트 하나만 허용하며, 호스트 서비스가 살아 있는 동안 라이브러리 정리를 끝냅니다. OpenSSL 할당만 세며 어댑터 C++ 객체와 호출자의 버퍼는 포함하지 않습니다.
- wolfSSL과 Mbed TLS도 메모리 모드에서 호스트 할당 함수를 사용합니다. 두 라이브러리의 공식 설정 함수에는 사용자 인자가 없으므로, 각 어댑터는 한 역할 프로세스에 메모리 모드 컨텍스트를 하나만 허용하고 비소유 `thread_local` 연결 포인터를 해당 컨텍스트가 살아 있는 동안만 둡니다. 정리할 때 라이브러리 내부 메모리를 먼저 해제한 뒤 기본 할당 함수로 되돌립니다. wolfSSL과 Mbed TLS가 요청한 메모리만 세며 어댑터의 C++ 객체와 호출자의 버퍼는 포함하지 않습니다.
- 협상값 가운데 공개 조회 API로 직접 확인하지 못한 값은 어댑터의 고정 허용 목록에서 추론하거나 빈 값으로 남깁니다. OpenSSL 서명 필드는 현재 빈 값입니다. 이 차이를 실제 메시지별 관측 정확도라고 주장하지 않습니다.
- 메모리 훅 단독 시험은 셋업과 정리만 확인합니다. 전체 측정 경로의 메모리 검증은 프레임워크 통합 실행에서 따로 확인해야 합니다.

## 시험용 인증서와 단독 시험

`scripts/make-pki.sh <출력 폴더> [ecdsa|rsa|ed25519] [1|2|3]`은 로컬 CA와 서버·클라이언트 인증서를 만듭니다. 기본값은 ECDSA, 체인 길이 2입니다. 길이는 루트를 제외하고 잎 인증서를 포함한 개수입니다. 루트와 중간 CA는 P-256이며, 선택한 알고리즘은 서버·클라이언트 키에 적용됩니다. 생성은 무작위 키를 쓰므로 파일의 바이트 단위 재현을 의미하지 않습니다. 같은 폴더를 다시 지정하면 해당 시험 키를 새로 만듭니다.

단독 시험 실행 파일 `turtle_adapter_smoke CLIENT.so SERVER.so PKI_DIR [mutual] [native]`는 실제 루프백 TCP에서 TLS 1.3과 인증서 검증, 협상 프로필, 암호화된 32바이트 왕복 통신을 확인합니다. 이것은 프레임워크의 새 역할 프로세스·격리·계측 실행을 대신하지 않습니다. `turtle_adapter_memory ADAPTER.so PKI_DIR`는 새 프로세스에서 할당 함수를 설치하고 셋업 이후 정리까지 할당이 실제로 관측되며 미해제 할당이 없는지 확인합니다.
